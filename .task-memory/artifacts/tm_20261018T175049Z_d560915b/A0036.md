Problem: the v2 session list is pull-only. SessionsController reads a page through SessionCatalogSource and updates only on an explicit refresh, a profile change or a load-more, so a session that starts, is renamed or is deleted elsewhere never appears without a manual refresh. That is the first unmet criterion of the parent V2-043 (#275) and the reason its V2-043B child (#365, the visible catalog) explicitly excludes 'live discovery'.

Objective: the session list reflects a session that starts, is renamed or is deleted elsewhere, without a manual refresh. The event is only a trigger; the list state is always the result of an authoritative GET /api/session re-read. One GET /api/event per endpoint is preserved.

Resolved decisions:
D1 - One stream per endpoint. The catalog takes a lease on the existing per-profile slot instead of opening a second subscription. The lease holds the slot (the slot's refcount counts catalog leases and live handles), probes 2.0.22 like a live lease and never calls watch. The last lease and the last live handle together close the stream.
D2 - The identifier is V2-043C; the plan's V2-043 child table gains the line and #391 is retitled.
D3 - The trigger set is session.created, session.forked, session.renamed and session.deleted. The signal is payload-free: it carries no id, title, location or payload.
D4 - The signal is emitted at the start of OpenCodeStreamOwner._onFrame, before the global branch, before _routeChild and before the watch filter, and only for a frame whose type is one of the four.
D5 - The re-read is a quiet authoritative sync: from the head (cursor null) to the depth already loaded (max(1, _pages), capped at the existing 10 pages and 200 rows), following the fresh cursors of that traversal, validated exactly like the current read, and applied all-or-nothing so the list never mixes a new page with an old one. It sets neither loading nor stale, shows no progress, and clears the expanded row only when the session is no longer in the result. The manual refresh keeps its current contract.
D6 - The policy: a 300 ms debounce that is not reset by later triggers, a 2 s cooldown counted from the end of a sync to the start of the next, multiplied by 2^consecutive failures, at most two live timers, and a single pending sync. A trigger that arrives during a sync never cancels it: it becomes exactly one final sync. An explicit refresh cancels the sync and covers the earlier triggers; an explicit loadMore cancels the sync, keeps the pending trigger and the final sync re-reads to the new depth; a profile change invalidates everything.
D7 - The failure states: a failed sync keeps the rows, does not change the catalog failure and moves the list to behind (the existing liveStale notice). Three consecutive failures or a rate limit suspend the automatic sync until a successful manual refresh or a new profile selection; a reconnect does not lift the suspension. authenticationRequired clears the list as today and closes the source and the lease. invalidCursor inside a sync counts as a failure and keeps the previous rows. The list is current only when the feed is connected, a read that started after the last connection succeeded, no trigger arrived after that read started, and nothing is suspended.
D8 - The feed's lifetime: it opens after the first successful authoritative read of the selected profile and only while a SessionsPage is attached; it closes on a profile or credential change, on an authentication failure, when the last attach detaches and on dispose. A platform without IO, or without a directory, stays off (the pull only, no notice).

Risks and mitigations:
- The shared stream is the app's most used path. Mitigation: the lease adds no behaviour to the live view; the existing live suites must stay green unchanged, and the extraction is mechanical and reviewed separately.
- The live factory is at the size guard. Mitigation: the extraction comes first and the import_rules check is the gate.
- The owner change touches the shared harness package. Mitigation: the signal is additive and payload-free, the watched path is untouched, and the harness suites plus the fake-harness tests cover it.
- The re-read resets the pagination depth. Mitigation: the traversal follows the depth already loaded, the rows are applied all-or-nothing, and the expanded row is preserved while present.
- A suspended sync hides a live list. Mitigation: the notice is explicit (liveStale) and the manual refresh is the documented way out.
- A late frame from a previous connection triggers a new sync. Mitigation: the epoch and the existing generation fence.

Assumptions and fallbacks:
- The four lifecycle types are the ones the 2.0.22 server publishes for the list. If a live capture shows a different type, the codec is the single place to change; the re-read is harmless for an unknown type.
- A second concurrent subscription is the documented fallback if the shared-stream extraction proves unsafe; it would need an explicit deviation record for the one-stream-per-endpoint decision.
- The list is server-wide today; a project-scoped list must filter the trigger on data.location.directory.
