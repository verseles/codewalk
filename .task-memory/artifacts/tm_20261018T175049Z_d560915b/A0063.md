V2-043F planning, batch 1 of 3: helperCodex-6-luna-max, helperCodex-6.1-sol-xhigh-F and helperDeepSeek-41-flash-high.

CONSENSUS OF THE THREE PLANS: the five commands ship in the harness package only, with no change under lib/ (the profile slot is already 1,467 lines, below but close to the 1,500-line guard, so it cannot host new code); every attempt produces an OriginalCommand, a CommandReceipt and a typed failure; a receipt confirms only the response, never the effect, and the effects (session.renamed, session.deleted, session.viewed) are observed through the stream or an authoritative re-read, with no waiting and no retry; the domain vocabulary is additive only, with MutationOperation gaining a rename and an unread-marker member and no existing member changing meaning; archive stays the local-hide operation, because v2 HTTP has no archive field; the client never mints a session id, it passes through a caller-supplied one or omits it and lets the server mint; the commands are version-gated and fail closed, sending nothing to a version that did not define them; and the documentation is CODEBASE.md plus the harness README, with BEHAVIOR.md deliberately untouched because this unit adds no user-visible behavior.

helperCodex-6-luna-max: five separate clients (a create, an update/rename, a remove/delete, a fork and a view client) in packages/harness_opencode/lib/src/, each following the interrupt and prompt client pattern, with MutationOperation extended with rename and view; the encodings as the contract states, including location.directory always in the create body; the statuses 400, 401 and 404 mapped to a typed harness failure; the receipts capturing the exact mutation, the request id and the ownership verification; the tests for each encoding, each status, the version guard and the ownership check; and the risk that the server's working-directory fallback differs from the explicit location.directory, mitigated by always sending the directory.

helperCodex-6.1-sol-xhigh-F: one client with five explicit methods (create, rename, deleteSession, fork and markViewed) sharing only the HTTP execution, the bounds and the result classification, without refactoring the existing clients; the five operations authorized exclusively for the connected version 2.0.22 normalized by the existing parser, with the general compatibility table untouched; MutationOperation.rename and MutationOperation.markViewed added with the existing meanings of create, fork, delete and archive preserved; create and fork additionally returning the validated SessionSummary of the response, while the receipt confirms only the answer to the command and never a catalog update, a completed cascade delete or an observed event.

helperDeepSeek-41-flash-high: one client and one new file, session_lifecycle_client.dart, with the five methods over one private sender, because the five share the version gate, the deadline, the cancellation, the status mapping and the receipt construction, and five classes would duplicate about 120 lines each; the receipts are not effects, with create and fork returning the projected SessionSummary from the 200 body as authoritative response data and rename, delete and markViewed returning no data; the domain gains rename and markViewed immediately before unknown, with LifecycleFacet unchanged; the gate is exactly 2.0.22 by the same fail-closed rule as the interrupt and prompt clients, because ADR-023 forbids sending to a version that did not define the command, and the contract rows exist in 2.0.21 but only 2.0.22 is tested; the attempt retains the exact body for a later same-id replay; the harness README and CODEBASE.md are updated while BEHAVIOR.md is left unchanged on purpose.
