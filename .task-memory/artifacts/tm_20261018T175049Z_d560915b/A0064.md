V2-043F planning, batch 2 of 3: helperGrok-47-medium, helperSpace-bunny-max and helperMuse-spark-13-xhigh.

The three plans converge with the first batch on the whole surface: one harness client with five methods, the two additive domain operations, the receipts as admissions rather than effects, the exact-2.0.22 gate, no id minting in the client and location.directory always in the create body.

helperGrok-47-medium: one client named OpenCodeSessionLifecycleClient with five methods; explicitly no HarnessAdapter.create, no LifecycleFacet and no CapabilitySet call, because the sibling mutation clients authorize only a harness match while a session's metadata ownership is always unknown, so the capability guard would deny every call and a later row-action unit owns the authorization. Each call returns one OpenCodeLifecycleAttempt: the immutable OriginalCommand, a CommandReceipt, the exact JSON payload only when bytes were handed to the transport, and a SessionSummary only when a contract 200 body was parsed; the client never replays, persists, retries or updates the catalog. The receipt vocabulary is explicit: accepted is the admission of this HTTP exchange and not proof that a session was created, that children were deleted or that the unread badge cleared; nativeRef on accept is an identifier from the exchange (the returned id, or the target id when the success body is empty) and not a settlement proof; rejected is a definite refusal known from the status alone; uncertain means the server may already have applied the command; unavailable means nothing was sent. The domain gains rename and markViewed immediately before unknown, without reusing or redefining archive. The create body always carries location.directory and never a directory header, and the agent, model, metadata, permissions and parentID are not fields on this request, so they cannot be silently dropped; a later create-flow unit extends the request if it must send them. Only a parsed version whose toString is 2.0.22 may be sent, including a build suffix, and 2.0.21 stays unsent even though the OpenAPI document is byte-identical.

helperSpace-bunny-max: one client and one shared skeleton in packages/harness_opencode/lib/src/session_lifecycle_client.dart, because the five commands share the transport, the connected version, the 20-second deadline, the body bound, the ownership assertion, the command and receipt construction and one status vocabulary, so five clients would duplicate about 180 lines each and fork the vocabulary; the file lands near 500 lines. The domain gains exactly two operations, rename and markViewed, appended immediately before unknown, with no exhaustive switch over MutationOperation and no ordinal persistence, so no existing member changes meaning. The receipts are receipts: accepted means the endpoint answered with this command's success status for this exact request, and never proves the effect, since a rename's 204 does not prove the catalog shows the new title, a delete's 204 does not prove the rows are gone, a fork's 200 does not prove the history was copied and a create's 200 does not prove a new session exists, because the same-id create returns the existing session; only create and fork carry the observed SessionSummary, and the catalog re-read stays the authority. The gate is exactly 2.0.22, because the policy minimum and the tested 2.0.21 are insufficient: the fork shape, the view body and the same-id create semantics are verified only on the 2.0.22 anchors. The transport carries a caller-supplied session id and never mints one, always sends location.directory because the header is ignored by the native create and the fallback is the server's cwd or HOME, and retains the exact body so a same-id replay repeats it byte-identically.

helperMuse-spark-13-xhigh: one transport client with five explicit methods (create, rename, remove, fork and markViewed), reusing the interrupt and prompt receipt pattern with accepted, rejected, uncertain and unavailable and never proof of effect; two new MutationOperation members (rename and markViewed) with the existing meanings of create, fork, archive and delete unchanged; all five gated on exact 2.0.22, sharing a 20-second deadline and bounded bodies, never retrying, never hitting a live server, and resolving every confirmation by re-reading the authoritative state or the stream instead of trusting the receipt.
