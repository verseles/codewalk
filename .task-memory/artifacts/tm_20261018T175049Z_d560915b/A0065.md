V2-043F planning, batch 3 of 3: helperGemini-38-flash-high and the frontier helper.

helperGemini-38-flash-high: one cohesive client OpenCodeSessionLifecycleClient in a new session_lifecycle_client.dart, exported by the package, with the five operations, sharing the network bounds, the version check and the error mapping, at about 350 to 450 lines. Its proposals: a distinct typed attempt per operation (OpenCodeSessionCreateAttempt, OpenCodeSessionRenameAttempt, OpenCodeSessionDeleteAttempt, OpenCodeSessionForkAttempt and OpenCodeSessionViewAttempt), each carrying the command, the receipt and the operation's output (the SessionSummary for create and fork, the payload for auditing). A receipt proves only that the server received and accepted the mutation; the settlement comes from the SSE frames (session.created, session.renamed, session.deleted, session.forked and session.viewed) or from an authoritative re-read. The domain gains rename and markViewed, with the existing members keeping their position and meaning and archive remaining the local hide. The encodings: the create body carries location.directory always and the optional id and title; the rename body carries the title; the delete has no body; the fork body carries the optional before; the view body carries the idle. The status mapping: 200 and 204 accepted, 400 rejected as a protocol error with InvalidRequestError, 401 and 403 rejected as an auth error with UnauthorizedError, 404 rejected as a protocol error with SessionNotFoundError, 429 rejected as a rate limit with RateLimited, and any other status uncertain.

The frontier helper (helperClaude-opus-5-xhigh-F): one client with five public methods over a private send core that copies the interrupt client's pattern (its own token, the expiration completer, the Future.any, the late-response cancellation and the finally that cancels the timer, the listener and the response), with one attempt type for all the methods and no five classes, because the HTTP path is identical. A receipt is not proof of an effect: the effects come from the stream (the catalog change and the re-read) or from the time.viewed re-read, the Session.Info returned by create and fork is the server's record at admission and not a live state, and no method retries, replays, persists or reads for reconciliation. The domain gains rename and markViewed immediately before unknown, so the indices and the meaning of the existing members stay intact; archive keeps meaning the local hide and no archive command is sent. The gate is exactly 2.0.22, like the other mutation clients, and any other version answers unavailable('unverifiedVersion') without touching the network. The harness never mints a session id: create accepts an optional nativeSessionId from the caller, validated by openCodeSessionId, and without one the body omits the id key, so an uncertain receipt of such a create cannot be safely repeated and only resolves by reconciliation, outside this unit. With an id, the recorded matrix (b/create-matrix.json) shows that a replay with changed fields returns the original session with the new fields ignored, so a 200 whose title or location.directory differs from the intent becomes a rejection with the reason SessionIdentityOccupied and the action refresh. The create body carries only id, title and location.directory; the agent, model, metadata, permissions and the 2.0.22 parentID are never sent, and a request that carries a selection or metadata is refused as an unsupported create instead of silently dropping the fields. The error bodies are never read, because native messages echo ids and paths; the raw message is always empty and the reasons come from a fixed vocabulary with no directory, title, id, URL or token. Nothing blocks this unit: fork and view have no live recording, so they are tested against fakes in the contract's shape and the missing recording is recorded as a risk.
