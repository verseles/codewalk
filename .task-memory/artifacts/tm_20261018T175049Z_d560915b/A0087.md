V2-043H planning, batch 2 of 3: helperGrok-47-medium, helperSpace-bunny-max and helperMuse-spark-13-xhigh.

The three plans join the first batch on the substance: the project comes from the directories the endpoint already reported (the list's own groups), the request carries the canonical directory in the body and at most the title, the client mints no identifier, the receipt is an admission and the new session arrives with the next authoritative read, and a refused or uncertain create says so and is never replayed.

Their contributions beyond the first batch:
- helperGrok-47-medium: the create is a single dialog (a sheet on a compact width, a dialog on a wide one) with the project list, the title field and the confirm action; the project entries are the canonical directories the endpoint reported, each with the sessions it already holds, so the user creates inside a project the list knows. The flow never offers a free-form path, and an endpoint that reported no project offers no create at all, because there is no canonical directory to send. The title is optional and empty by default, so the endpoint names the session.
- helperSpace-bunny-max: the create goes through the same command path as the other actions, so it shares the exactly-2.0.22 gate, the profile's credential, the pre-dispatch revalidation and the typed refusal. The row that appears is the endpoint's record from the re-read, never the receipt's copy. The same-identifier rule is untouched because the flow sends no identifier.
- helperMuse-spark-13-xhigh: the create is offered only when the list is the endpoint's current answer and no command is in flight, with the same reason vocabulary the other entries use; the create's own receipt never adds a row, and a refused create leaves the list exactly as it was.
