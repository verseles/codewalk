2. Problem

Three section-27 requirements are absent:

- `EndpointProfileRepository` and the Servers UI cannot edit saved profile names or URLs.
- `WorkspaceStore` has no independent local default; profile rows lack visible Active/Default metadata.
- Settings opens `/hosts` without revealing or highlighting `hosts-search`.

URL editing creates an additional correctness obligation. Existing outbox records lack endpoint provenance, native slots use `profileID|endpoint`, and retained controllers/read callbacks do not distinguish A→B→A bindings. An old command or response could consequently acquire meaning at a different connection.

The correction must preserve normal uncertain-prompt reconciliation for unchanged legacy profiles, rather than disabling all existing outboxes.

3. Objective

Deliver these observable results:

- Each profile appears once with name, URL, health, and wrapping Active/Default/applicable authentication metadata. Filtering, order, keyboard activation, unhealthy rejection, and single-flight selection remain intact.
- Overflow supports Edit and independent Set/Clear Default alongside existing Check/Delete/Password/Pair/Renew. Neither editing metadata nor changing the default activates a profile.
- Name-only edits preserve connections and observations. Every acknowledged URL change creates a new persisted binding generation, including proxy-path changes and A→B→A.
- Previous-binding leases, queued sends, reads, replay, cancellation, delivery changes, message ownership, and first-prompt handoffs cannot operate as the new binding. Saved drafts, tabs, contexts, and operation records remain preserved.
- Settings search reveals, focuses, and highlights the Servers filter through `/hosts`, without inserting its query into that filter. Ordinary `/hosts` navigation remains ordinary.

4. Context and Constraints

**Verified evidence:**

- `endpoint_profile_store.dart` serializes operations and checks creation ownership, but removal deletes the item and leaves no retired-ID marker. The repository can therefore accept a previously removed ID again.
- `HostsController._id` mints 128 random bits; normal add-after-delete creates a new identity. This supports trusted production history, but does not establish provenance for arbitrary injected records.
- `prompt_outbox_store.dart` persists payload, version, command, message ID, and cancellation state, but no endpoint. Reconcile/cancel/switch use the current client; composer chips match entries by message ID alone.
- Native slots await `ready()` before leasing without a subsequent current-binding check. `close()` caches `_shutdown()` through `??=`, so explicit synchronous revocation must precede asynchronous teardown.
- GoRouter is pinned to `18.0.2`; installed source confirms `push(..., extra: ...)` and `GoRouterState.extra`. The application redirect rejects query-bearing `/hosts`.

The existing vault deliberately scopes credentials by normalized origin, profile ID, and credential kind; proxy paths share an origin. Its tests explicitly prove this behavior. Editing must leave every vault record untouched, then resolve credentials through the destination’s existing scope.

Retain ADR-001/023/058, full `SessionRef`, existing `SourceProvenance`, Android/Linux scope, max-eight warm views, max-32 tabs, pure-Dart core, and the 1,500-line authored-Dart limit. No general revision or persistence framework is needed.

5. Resolved Decisions

**Profile binding and metadata**

Add only `EndpointProfile.bindingRevision`, defaulting to zero when absent from historical records. Validate it as an integer in `0..0x7fffffff`; present null, wrong types, and out-of-range values are unreadable. Increment it only when the validated URL changes. A label-only edit preserves it.

Use `sameBinding` to compare ID, full endpoint, and binding revision. Expected metadata comparison additionally includes label. Existing controller catalog revisions fence stale UI and credential operations.

**Credentials**

Do not add a reauthentication flag, credential migration, or credential-read prerequisite for renaming. After a URL edit, read only the destination’s existing origin/profile/type credential:

- Existing credential B at origin B is valid destination-scoped material.
- Missing B produces the existing Password/Pair recovery state.
- Unreadable B remains preserved and unavailable.
- Credential A is never copied or supplied to B.

**Legacy provenance and removal/recreation**

Revision zero is sufficient only with explicitly trusted canonical production-profile context, not as a default for arbitrary outbox construction.

A concrete counterexample prevents treating zero as universal proof: save ID X at A, retain its ledger, remove X, then save X at B. Current creation accepts this because the index/item/current-origin credential checks are clear.

Close that future API hole with one non-secret per-ID retirement marker, written through the existing removal intent and checked by creation. Normal recreation continues minting a new ID. This adds no edit journal and does not touch retained ledgers.

Trusted unchanged production profiles at revision zero retain legacy reconciliation. Unbound entries at revision greater than zero, or without trusted context, remain locally readable/dismissible but cannot perform network operations. Do not stamp inferred endpoint provenance into legacy records.

**New outbox provenance**

Persist both the validated full client endpoint and binding revision on every new record. Require both to match the current binding. Endpoint alone would permit an A0 record to revive at A2 after A→B→A.

**Defaults and navigation**

Keep the default solely in `WorkspaceStore`. Restoration priority is valid launch tab → saved active → valid default → first saved profile. Default changes do not trigger selection.

Use a recognized serializable router-extra tag while the URI remains exactly `/hosts`; do not broaden external-link syntax.

8. Risks and Mitigations

- **Cross-endpoint command mutation or false ownership:** endpoint-plus-revision records, trusted legacy policy, current-slot token, cancellation propagation, and eligibility-aware composer matching.
- **Legacy provenance overclaim:** zero alone is insufficient. Require explicit trusted production context, reject future retired-ID reuse, and keep arbitrary/unproven legacy data unavailable without rewriting it.
- **Unknown-write data loss:** exact readback acknowledgement, raw-field preservation, queue-internal uncertainty checks, and reconciliation before deriving subsequent state.
- **Late acquisition or ABA revival:** persisted binding revision, permanently revoked runtime tokens, post-await checks, and completed teardown before replacement ownership.
- **Local-data or UX regression:** preserve canonical keys and saved records, isolate runtime invalidation, retain current `notFound` policy, and test compact/RTL/2× rendering.

9. Assumptions and Fallbacks

**Legacy history:** the supported pre-edit production path minted fresh random profile IDs and provided no URL-update API. Present files cannot prove provenance for arbitrary manually recreated/injected historical IDs. Such contexts must not enable legacy trust; this is a technical evidence boundary, not a reason to disable ordinary canonical legacy profiles.

**Repository ownership:** production uses one serialized profile repository and one workspace store. Verify no additional enabled writer before implementation. These backend APIs do not provide cross-process atomic compare-and-swap; do not claim that guarantee.

**Credentials:** destination-scoped credentials remain authoritative. If missing, use existing Password/Pair; if unreadable, preserve them and expose retry. No metadata rename waits for vault readability.

**Persistence/lifecycle:** unresolved actual storage blocks dependent writes; failed retirement blocks replacement traffic. Preserve records and offer finite reconciliation/retry rather than rollback, mutation replay, or old-slot revival.

**Tool/API evidence:** pinned GoRouter extras and cancellation-capable prompt/read APIs were inspected locally. No external behavior is needed for the chosen design. Any newly discovered dependency on unverified behavior requires local pinned-source verification before implementation.
