helperCodex-6-luna-max: fix_required, medium risk, high confidence. The implementation follows the reviewed request shapes and keeps the receipts separate from the observed effects, but one status check accepts the success codes across the operations instead of enforcing each endpoint's documented response. Its finding (warning, correctness): a 200 response for rename, delete or mark-viewed is recorded as accepted, although those endpoints document only 204, so a caller can treat an out-of-contract response as admitted, including for delete. The evidence: the shared check accepts both 200 and 204 and the no-session branch records the acceptance without reading a body, while the contract specifies 204 for PATCH, DELETE and /view and 200 for create and fork (plan/11-opencode-v2-server-api.md:823, 830, 843, 912). The fix: pass the expected success status into the send per operation and classify the other statuses as uncertain, keeping 200 for create and fork and 204 for the rest.

helperCodex-6.1-sol-xhigh-F: approve, low risk, high confidence, no findings. The implementation adheres strictly to ADR-023 and to the architectural boundaries: the strict version gating to 2.0.22 correctly prevents sending unverified commands to an incompatible server, and the same-identifier occupancy rule properly detects and rejects the create replays where the title or the directory differs from the original session. helperDeepSeek-41-flash-high: fix_required, medium risk, high confidence. The five encodings and the exact 2.0.22 version gate match the pinned contract and the focused tests cover the main request, refusal and receipt paths, but four correctness gaps remain in the receipt and reconciliation contract, and the fixes are localized without a redesign of the client. Its findings:
1 (warning, correctness): a create that supplies a caller identifier and receives a different session id is accepted as admitted, so a later same-id reconciliation targets the wrong session and a duplicate can be adopted, while the README and the CODEBASE both promise that a response for another session is refused. The occupancy checks compare only the title and the canonical directory, the native identifier is never compared with the response's, and the create adds it without the identifier validation. The sibling prompt client rejects a response whose data id differs from the message id, and the recorded matrix shows a same-id replay returns the original id. The fix: compare the response's native id with the caller's when one was supplied, validate the caller's identifier before sending, and add the missing test.
2 (warning, correctness): the rejected and the uncertain attempts after the request was handed to the transport report the payload as null, so the adapter cannot persist the exact native encoding needed for reconciliation or replay equality, even though bytes may have been sent. The attempt's payload is documented as the exact body handed to the transport, and the prompt and form-reply clients retain it on every post-send outcome. The fix: capture the encoded payload before the send and pass it to every finish after the encoding, with a test for a rejected or uncertain rename carrying a non-null payload.
3 (warning, correctness): the authentication failures cannot carry the authenticate action, a missing session cannot carry the refresh action, and a 429 is marked non-retryable, so the later row-action user interface receives weaker typed failures than every sibling mutation client. The sibling clients set the authenticate, refresh and retryable hints. The fix: extend the rejection with the action and the retryable flag, map 401 and 403 to authenticate, 404 to refresh, 429 to retryable, and the identity occupancy to refresh.
4 (warning, correctness): a 200 from a non-conforming or misrouted endpoint is recorded as an admitted rename, delete or view, although the 2.0.22 contract returns 204 only, so the receipt can claim an effect that never happened. The sibling clients accept only 204 for a no-content command. The fix: require the expected status per command and treat any other status, including a 200 on a no-content command, as uncertain or as a protocol rejection.
5 (suggestion, edge_case): the 4 KiB default response cap is sized for the interrupt client's tiny body, while create and fork return a full session record with optional metadata and permissions, so a valid response over the cap becomes uncertain after the mutation may already have succeeded and an unidentified create loses the minted id. The reader defaults to 1 MiB and the endpoint probe to 64 KiB for comparable records. The fix: raise the default and add a test with a large record.
6 (suggestion, edge_case): the create identifier and the free-form title and boundary values are neither validated nor size-bounded before they are encoded and sent, so malformed or oversized caller input reaches the wire and returns a generic 400 instead of a local typed refusal. The fix: validate the identifier and bound the text fields before building the request.
