Orchestrator assessment of the V2-043G planning round (seven of the eight eligible helpers delivered a plan; helperGemini-38-flash-high's first delivery was lost, its first recovery was lost too, and the plan was recovered through the part protocol, so it is judged on its content).

AGREED BY EVERY PLAN: the row offers the five actions (rename, delete with the children-cascade warning, fork from here, mark as viewed and hide or show in CodeWalk), the read history and the open live stay in the expanded row and are not duplicated, the menu is the v2 tree's own widget and the retained v1 menu is a reference and not a port, the fork copies the whole history because the row has no message boundary, the unread comes from the endpoint's viewed against idle and not from a local attention, the local hide is a local store, no server action patches a row, and the core capability guard is not weakened.

DECIDED ON THE EVIDENCE
D1 - The action surface: one trailing overflow control on the row (a 48 dp target, the more_vert icon, a localized tooltip and the key session-actions-<storageKey>), which opens a vertical menu with an icon and a localized label; the same menu also opens by a long press on the card (compact), by the secondary tap and by the context-menu key or Shift+F10 on the focused row (desktop), and through a semantics custom action; the tap still expands the row; the entries are mark as viewed (only on an unread row), rename, fork from here, hide or show in CodeWalk and delete in the error colour. A native entry that is not available is disabled with its reason as the subtitle, and an action the endpoint does not define never appears, because 2.0.22 exposes no archive write.
D2 - The authorization: the core guard is not changed and no ownership is inferred. The v2 platform builds a capability set from the verified evidence (the probed version exactly 2.0.22 whose stable routes are in the versioned contract, the IO platform and a usable credential) with the names history.rename, history.delete, history.fork and history.markViewed; before the probe or with another version they stay unknown or unavailable with a reason; the action's availability combines that capability with the row's state (the list is current, no command is in flight, the marker is present); the capability is never discovered by trying a mutation, because the probe is the profile's own GET /api/info; the ownership label keeps answering unknown and authorizes nothing, and the ownership dimension of the plan's effective-capability rule is documented as not applicable to the endpoint's record operations. Six plans propose this, including the frontier helper; the seventh (helperSpace-bunny-max) proposes extending the core guard with a freshness-bound mutation-authority proof instead, and the judge rejects that for this unit: it widens the shared domain for a unit that does not need it, while the plan's promise that the actions come from capabilities is already honoured by the platform's own capability set, read by the same code that renders the entry and enforces the command.
D3 - The unread marker: the session projection records the endpoint's idle and viewed epochs in the session metadata (the valid integers only, and an absent or invalid value leaves the key absent without failing the page); a pure helper derives the marker; the row shows a small dot with the localized unread text and the key session-unread-<storageKey>; the mark-as-viewed sends the row's observed idle, which is safe against a race because the endpoint never marks a newer idle as seen; the dot disappears only when the endpoint returns a viewed epoch at or after the idle; and the session.viewed event joins the catalog change kinds, so a view made in another client also triggers the quiet re-read.
D4 - The delete: a confirmation that names the session, says the action cannot be undone and that a running execution is interrupted; the cascade warning counts the direct children with the bounded read, showing the exact count, the at-least form at the bound, or no count line when the read fails, and the delete stays disabled until the count resolves; an authentication failure closes the dialog; the confirmation revalidates the row and the capability and sends one delete; while it runs the row stays visible with a pending state and that row's menu and buttons are disabled, while the other rows, the refresh and the Load more stay normal; the accepted receipt asks for the quiet re-read, which is where the row's disappearance is observed.
D5 - The local hide: a store on the v2 metadata store under a cw2. key, holding the session storage keys, bounded, read at startup, never overwritten when unreadable, never written before the first read and applied only after a successful write; the filters are active (the default), hidden and all; the hide is write-first, so a failed write leaves the row visible.
D6 - No optimistic row patching: the v1 optimistic rename and delete with its rollback is not ported, because the v2 rule is that a command's effect is observed only by the quiet authoritative re-read; the row shows a pending state, a failed command therefore needs no rollback, and an uncertain receipt is reconciled and never replayed. One plan proposes porting the v1 optimistic behaviour; the judge rejects it against the v2 decisions that the list is a pure projection of the authoritative read and that a command's effect is never patched into a row.
D7 - The fork omits the before boundary, because the catalog row has no timeline position.

REJECTED, with the reason
Extending the shared core capability guard with a mutation-authority proof (helperSpace-bunny-max): it widens the shared domain for a unit that does not need it, and the plan's promise that every control is driven by capabilities is already met by the platform's own capability set, read by the same code that renders the entry and enforces the command. The v1 icon grid as the v2 menu (rejected by the same helper): it does not survive a 2x text scale, long localized labels or right-to-left. The v1 local unread attention as the v2 marker: it is a different concept from the endpoint's viewed marker and the plan asks for the endpoint's. And the v1 server-side archive: 2.0.22 exposes no archive write, so the hide is local.

ACCEPTED TRADOWNS
The action that is not available is disabled with its reason rather than hidden, so the row's shape does not change with the state; the mark-as-viewed entry disappears entirely when there is nothing to mark; the delete's count is not a lock, because the endpoint deletes every child it finds; the fork copies the whole history; the hide is reversible from the hidden filter; and the fork and the mark-as-viewed have no live recording in the 2.0.22 fixtures, so they are proven against fakes in the contract's shape only.
