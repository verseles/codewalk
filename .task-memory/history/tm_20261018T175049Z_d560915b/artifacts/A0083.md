helperGrok-47-medium: fix_required, medium risk, high confidence. The row actions follow the 2.0.22 commands, the cascade confirmation and the local hide, but the committed controller never clears an uncertain command and applies an in-flight result after a profile change, and an optional unread epoch can also fail the whole session page. Its findings: (1, warning, correctness) after one uncertain receipt the list shows the working notice for the rest of the controller's life, including after a successful re-read and after switching profiles, because the flag is only set and never assigned false, the clear resets only the failure and neither the quiet read nor the refresh clears the latch; the fix is to clear it in the clear, when the quiet read applies a page and when a head refresh succeeds. (2, warning, concurrency_async) switching profiles while a command is in flight writes that outcome onto the new profile, a false failure, a stuck notice or an extra re-read, because after the awaited command the controller updates its state with no check that the source is still the current one; the fix is to return without touching the new profile's notices or the live latch, and to do the same in the local hide. (3, warning, correctness) one unusable idle or viewed value fails the projection and the session list read fails instead of omitting the marker, because the guard compares a millisecond value with the microsecond limit and hands the product to the date constructor with no catch, and every row of the catalogue read goes through it.

helperSpace-bunny-max: fix_required, medium risk, high confidence. The row actions are implemented end to end and the transport half matches the pinned session protocol, the authorization fence, the no-row-patch rule, the bounded and fail-closed local hide and the unread marker on the summary all hold, but a transient probe failure leaves every native action disabled until the user manually refreshes, which contradicts the fix commit's own claim. Its findings: (1, warning, correctness) after a slow or failed probe the catalogue still reads fine but every row action stays disabled with the version not verified until the user presses refresh or re-selects the profile, because the support is probed only from the refresh path and the automatic re-read never restores it; the fix is to re-probe the support when an authoritative read succeeds, which costs no extra request in the normal case because a definitive answer is cached. (2, suggestion, correctness) after an uncertain command whose reconciliation read failed, a later successful manual refresh clears the stale notice but leaves the working banner forever, because the manual read path never resets the flag; the fix is to reset it in the manual read's successful path too. (3, suggestion) the child count's bound.

helperMuse-spark-13-xhigh: approve, low risk, high confidence, no findings. The unit delivers the catalogue row actions behind the endpoint contract with disabled-with-reason entries, a count-gated delete and a fail-closed local hide, and no high-confidence correctness, security or architecture defect was found. Its accepted tradeoffs: the support is probed once per profile and cached, a mid-profile server upgrade needs a profile switch; the delete stays disabled until the direct-children count is known; no command patches a row and the effect is observed by the quiet authoritative re-read with a revalidation before the send; and the local hide is CodeWalk-only under a bounded key, fail-closed and applied only after a successful write. Its non-issues: the no-idle-marker reason is never produced because the mark-as-viewed entry is hidden without an unread row, which is a harmless dead path; the menu stays enabled while a quiet re-read is pending and the dispatch refuses the stale rows with a failure notice, an intentional anti-flicker; and the pull-only staleness of the viewed epoch only costs an extra tap.
