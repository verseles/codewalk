2. Problem

- The v2 profile store is create-only and has no edit port (`endpoints.dart` port: `load/save/readSecret/readCredential/saveCredential/replaceCredential/remove`); `EndpointProfileStore._save` rejects an existing id. A saved profile cannot be renamed or re-pointed.
- The v2 catalog has no local default server: `WorkspaceStore` persists only `active`+`projects`; the only default-server code on `main` is retained v1 (`app_provider.dart:1455`).
- The Servers row shows no visible Active/Default/auth metadata and the overflow is `check/remove/pair/renew/password` (`hosts_page.dart:21`) — no default selection, no edit.
- Settings search → Servers pushes plain `/hosts` (`settings_shell_page.dart:245`); there is no reveal/focus/highlight of `ValueKey('hosts-search')`.
- **Material defect (R1):** a URL edit creates a NEW transport binding while the profile id, session refs, drafts, tabs and outbox ledgers survive. `prompt_outbox_store.dart` keys ledgers by session only (`keyFor` = sha256 of `SessionRef.storageKey`, which embeds host/harness/nativeId) and every mutating path uses the **current** client: `reconcile`→`reader.locatePrompt`+`client.post` (528-606), `cancel`→`client.cancelInbox` (309), `switchDelivery`→`client.switchInboxDelivery` (352). A record created against endpoint A is therefore reconciled/cancelled against endpoint B.
- Secondary defects this unit must not inherit: `WorkspaceStore._update` keeps a stale cache when a write throws, so a queued write can overwrite a committed-but-thrown update; `app_navigation_controller.prepareLink` rejects any query, so `/hosts?target=…` resolves to `/unsupported` (`app_navigation_controller.dart:88-95`).

3. Objective

- A saved profile can be renamed and re-pointed in place (id, drafts, tabs, session identity unchanged); the edit is fenced by the exact expected profile and confirmed by read-back before success is claimed; the vault is never touched.
- A local default server can be set/cleared independently of the active server, survives restart, and is used only as a restore fallback (launch tab → last active → valid default → first saved); setting it never switches the server.
- Every profile row shows wrapping metadata: Active, Default, and the applicable authentication kind, plus the existing URL/health/expiry.
- The overflow keeps Check, Password, Pair, Renew, Delete and adds Set/Clear default and Edit.
- Tapping **or keyboard-activating** an inactive row selects it; repeated activations stay blocked while a switch is pending; known-unhealthy targets stay rejected; the acknowledged persisted active survives a later connectivity failure (already implemented — regression-protected).
- The inline filter still matches name/URL/profile id, preserves order and the active/default choice, and clearing restores the full list (already implemented — regression-protected).
- Settings search reveals and highlights the server-selection filter through the existing Servers destination, without seeding the profile filter and without changing the external link syntax.
- After a URL edit: no old-generation operation (outbox read/replay/cancel/switch, lease acquisition, first-prompt handoff, warm live view, health assessment, route direct read) runs against the old binding, including after restart and after A→B→A; local records survive; re-authentication after an origin change is finite and concrete (existing Password/Pair repair).

5. Resolved Decisions

- D1 — **The local default lives in `WorkspaceStore`, as the sole authority.** The v1 envelope gains an optional `default` key (`{"v":1,"active":…,"projects":{…},"default":<id|null>}`); `_apply` treats an absent key as null and a malformed value as unreadable (preserved, never overwritten). No second store, no new key namespace, no envelope version bump (older readers ignore the unknown key).
- D2 — **Default is a fallback, never an override.** `WorkspaceController._retry()` priority: launch-tab host → saved active → default (only when the id is among the saved profiles) → first saved. A default write never touches `active` and never switches the selection.
- D3 — **The binding fence is one generation counter on the profile, and legacy records are judged by construction, not by provenance.** `EndpointProfile` gains `int bindingRevision` (default 0; every pre-existing profile is 0; it advances **only** on an acknowledged URL change, including a same-origin path change and A→B→A). The outbox record stores `bindingRevision` + the full endpoint URL; the effective revision of a record without the field is **0 by construction** (the field did not exist before this change). An operation is allowed only when `effectiveRevision == currentRevision` **and** (the record has no endpoint ⇒ `currentRevision == 0`, else the record's endpoint equals the current full URL). No provenance is invented, no legacy entry is silently re-bound, and the unchanged-profile legacy path keeps working exactly as today.
- D4 — **The edit is a metadata-only patch of one record.** `EndpointProfileRepository.update(EndpointProfile expected, {required String label, required Uri endpoint})`; the store compares the stored item with `expected` (id, label, endpoint, bindingRevision) and rejects with `Profile changed; edit preserved.` otherwise; it computes `nextRevision = stored.bindingRevision + (endpoint changed ? 1 : 0)` itself (no forged increments), patches the **raw** item JSON (`label`, `url`, `bindingRevision`) so unknown/future fields survive, writes once, then re-reads and confirms the intended content before reporting success. On a write exception the read-back decides: matching ⇒ committed (success), otherwise ⇒ `Profile update unconfirmed; data preserved.` No journal, no probe, no vault access, no credential requirement.
- D5 — **The vault is untouched by an edit; the scope stays the authority.** After an origin change the profile reads only the credential scoped to (new origin, profile id, kind) — normally absent, so the profile is finitely unauthenticated and the existing Password/Pair repair re-authenticates it; a credential already stored for the destination origin is that origin's own credential, not a transfer. No purge, copy or migration of vault records; the old origin's record stays where the scope put it. No blanket re-authentication gate is introduced, and a rename never requires a readable credential.
- D6 — **Unknown writes are reconciled by read-back, inside the executor.** `WorkspaceStore._update` re-reads the authoritative envelope **inside** `_executor.run`, rebases the pending mutation onto the stored state (so a queued active/project/default write cannot overwrite a committed-but-thrown earlier update), rechecks the unreadable gate there, and after a write exception re-reads: equal to the intended snapshot ⇒ committed (cache updated, error cleared), otherwise ⇒ uncertain (error kept, **no** blind retry, **no** rollback). The profile store uses the same read-back confirmation (D4).
- D7 — **Every network operation is fenced by the current binding, checked before the call and after each await.** `OpenCodePromptOutbox` gains `required EndpointProfile profile` (the decoded profile — production always has one, so revision 0 is never assumed) and an injected synchronous `EndpointProfile? Function()? currentProfile` supplier; the slot implements it as "null when the slot is closing, the profile is gone, or the current revision differs". Every `locatePrompt`, `post`, `cancelInbox`, `switchInboxDelivery` is preceded by the check and repeated after each await; a mismatch refuses with the existing finite vocabulary (`sourceChanged`), never a network call.
- D8 — **Slots are generation-scoped.** The slot key becomes `'${profile.id}|${profile.endpoint}|${profile.bindingRevision}'` so an A→B→A edit cannot revive the old generation's slot; the slot re-checks the binding after `_probe()` so a pending acquisition cannot attach a stream after a newer binding; closing the slot revokes its outbox synchronously.
- D9 — **Old-source entries stay inspectable and dismissible but cannot act.** `OutboxEntry` gains one read-only field (`sourceMatches`); the outbox computes it per entry. The composer's chip mapping only claims a pending row for a current-source entry (no coincident messageId takeover), and old-source rows render read-only (dismiss only, no cancel/check/switch). `dismiss` remains allowed: it is a local ledger mutation that prevents any later replay.
- D10 — **Binding changes retire endpoint-bound runtime state but keep local records.** The catalog invalidates and closes its source; the live controller adopts the new profile and detaches; health records whose generation differ are dropped; route direct reads/summaries are cleared; warm live views of the old generation are released while their tab/draft/context records stay; the pending first prompt's `wanted()` compares the generation, so an ABA (same id, URL and secret) still cancels the handoff. A label-only edit touches none of this.
- D11 — **The Settings reveal is a typed router extra, never a query.** `context.push('/hosts', extra: const HostsRevealFilter())`; `app_router` builds `HostsPage(revealFilter: state.extra is HostsRevealFilter)`; the URI stays exactly `/hosts`, so `prepareLink` accepts it and no external link syntax changes. `HostsPage` focuses `hosts-search` after the first frame and paints a bounded 2 s highlight; the filter stays empty (the Settings query is never seeded into it). The Settings search matching for Servers additionally includes the filter label (`l.serversSearchActiveHint`), and returning from Servers keeps the Settings query (the page is pushed, not replaced).
- D12 — **Copy discipline.** `serversActive`, `serversDefault`, `serversSetDefault`, `serversClearDefault`, `serversEdit` are ported from the retained catalog through `hosts_catalog.PORT_KEYS` (no new translation). Only genuinely new strings get 14-locale copy: one for the CAS rejection, one for the default conflict, one for the old-source outbox entry.

1. Rename: the stored label changes, the id/endpoint/revision stay, the vault is byte-identical, and the credential is still readable.
2. Same-origin path change: the revision advances by 1, the URL changes, the credential scope (origin) is unchanged and the stored credential still resolves.
3. Changed origin: the revision advances, the stored URL changes, the vault is untouched, and reading the profile yields no credential (the destination origin has none) — the row shows the auth-required state and the Password repair re-authenticates it.
4. Return to a previously used origin (A→B→A): the revision advances again (2), the old generation stays fenced, and the scope rule decides the credential (no cross-origin copy).
5. Stale expected profile (the stored label differs): the edit is rejected with the finite reason, the stored data is unchanged.
6. Unknown write (the metadata write commits then throws): the read-back shows the intent ⇒ success is reported; a write that fails before writing ⇒ failure with the data preserved; no secret ever appears in metadata.
7. Raw-JSON patch: an item carrying an unknown field keeps that field after the edit (future fields are preserved).
8. Default: set/clear persists across a restart (a new store instance over the same backend); a queued active/project/default write after a commit-then-throw does not overwrite the committed value; an unreadable envelope blocks the write instead of overwriting it.
9. Restore priority: launch tab wins; saved active wins over the default; the default wins when there is neither; the first saved wins when there is no default; setting a default never switches the current server.
10. Outbox, legacy record on an unchanged profile: the ordinary uncertain-prompt reconciliation still works (the legacy path is unchanged) — this is the regression guard for D3.
11. Outbox, old record after a URL edit: `reconcile`, `cancel` and `switchDelivery` refuse with `sourceChanged`, and **no** HTTP request is issued (assert on the fake client/reader).
12. Outbox, new record after a URL edit: a fresh deliberate send works, is recorded with the new binding, and reconciles normally.
13. Outbox, source change during persistence, during the replay backoff, and during cancel/switch: the check after each await refuses the operation; the record stays inspectable and dismissible.
14. Outbox, restart: a legacy record and a bound record are read back with their bindings; the legacy record is eligible only while the current revision is 0.
15. Outbox, old message id ownership: an old-source entry does not claim a new endpoint's coincident pending message id, and its row offers only dismiss.

17. URL edit during an old lease acquisition: the pending acquisition cannot attach; the new generation opens its own stream; one endpoint stream per profile is preserved (8 warm / 32 tabs).
18. Local records preserved: saved tabs, drafts and context records survive the edit; only the endpoint-bound runtime state is retired.

8. Risks and Mitigations

- **Severe — a pre-existing outbox record is replayed/cancelled against the new endpoint.** Mitigation: D3/D7 (the record carries its binding; every network path is fenced, refused with `sourceChanged`); tests 11-14 assert zero requests.
- **Severe — an old generation revives after A→B→A.** Mitigation: the revision is monotonic and persisted with the URL; slot keys include it (D8); the outbox compares revisions, not URLs; tests 16-17.
- **Severe — a queued workspace write overwrites a committed-but-thrown update.** Mitigation: D6 (re-read + rebase inside the executor, read-back acknowledgement, no blind retry/rollback); test 8.
- **High — the edit loses data or claims success without a write.** Mitigation: D4 (raw-JSON patch, exact CAS, read-back confirmation, unknown fields preserved); tests 5-7.
- **High — an edit silently moves a credential between origins.** Mitigation: D5 (the vault is never written; the scope decides; a destination-origin credential is that origin's own); tests 3-4 assert the vault is untouched and no secret is copied.
- **High — the Settings reveal lands on `/unsupported`.** Mitigation: D11 (typed extra, URI stays `/hosts`; go_router 18.0.2 `extra` verified in the installed package); test 22 asserts the final URI has no query.
- **Medium — over-refusal of legacy records hurts an unchanged profile.** Mitigation: D3 keeps the legacy path alive while revision 0 (test 10); over-refusal only starts at the first acknowledged URL change, which is the safe direction.
- **Medium — the composer loses the user's visibility of an old prompt.** Mitigation: D9 (entries stay inspectable and dismissible, read-only, with a finite reason).
- **Medium — file-size/architecture guard breaches.** Mitigation: `hosts_page.dart` is 560 lines; if the edit mode pushes it near 1500, split the dialog into `lib/features/hosts/profile_edit_dialog.dart`; the new files are tiny and feature-only (no harness imports).
- **Low — l10n drift.** Mitigation: the 14-locale generator plus `--check` in `make check`; only three new strings need copy.

9. Assumptions and Fallbacks

- **Legacy-record provenance (the draft's weakest point).** The draft's phrase "a trusted current production profile has bindingRevision0" could be read as inventing provenance. Refinement adopted (D3): a legacy record's effective revision is 0 **by construction** (the field did not exist before this change), and the current revision is read from the authoritative store. The proof rests on three verified facts: (i) the store was create-only, so every legacy record's source endpoint is the profile's creation endpoint; (ii) `SessionRef.storageKey` embeds host and harness, so a ledger belongs to exactly one profile id; (iii) profile ids are minted randomly and never reused (create-only store rejects an existing id; the importer writes `cw2.profiles.*`, never `cw2.endpointProfiles.*`). **No counterexample exists** for the unchanged-profile case; after the first acknowledged URL change the rule refuses (safe direction). What is *not* provable from the local tree: that no external producer wrote `cw2.outbox.v1.*` or `cw2.endpointProfiles.item.*` with a foreign shape — mitigated by tolerant decoders, the "unreadable is never overwritten" rule, and the existing fixtures.
- **Missing proof the draft left open — the authoritative current binding at operation time.** The draft names a revocation callback but no source of truth. Adopted: the outbox consults a synchronous `currentProfile` supplier injected from the composition root (the `HostsController` catalog) and the slot's own liveness; the check repeats after every await. If a supplier cannot be produced in some embedding, the fallback is the conservative "revoked" (refuse network), never "assume current".
- **Missing proof — the slot reuse after ABA.** The draft did not mention the slot key; `session_live_factory_io.dart` keys slots by `id|endpoint`, so A→B→A would reuse the old generation. Fixed by including the revision in the key (D8) and by re-checking the binding after the probe.
- **Missing proof — coincident message ids.** The draft's "old source entry cannot claim ownership" is enforced in the composer by filtering the chip map to current-source entries (D9); if a pending row's native id coincides, the row shows no local entry.
- **Origin/credential semantics.** Verified: origin = scheme+host+port, path excluded; the scope is origin+profile+kind. If the implementer finds a case where the destination origin must not reuse an existing credential, the change belongs in the vault scope (one place), not per call site; the fallback is stricter (never reuse across origins) and must be recorded, not assumed.
- **Persistence semantics.** The default is a plain string inside the existing JSON envelope (`V2MetadataStore` accepts strings); an unreadable envelope blocks the write. Fallback if the envelope must grow further: a separate optional key inside the same envelope (still one authority, still v1).
- **Lifecycle.** The retained live view re-opens through the existing `started == false` path (`session_live_page.dart:68`); no new auto-reconnect is introduced. If the page does not restart it, the user re-enters the session — an acceptable, bounded fallback.
- **Externals.** None needed: no server contract, SDK or schema changes; the pinned OpenCode 2.0.22 fixtures are untouched.
