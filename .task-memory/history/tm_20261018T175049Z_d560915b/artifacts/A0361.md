PLANNING R2:
1. Status

Ready — the integer `bindingRevision = 0` proposal needs one correction: a profile recreated with the same ID could reset to zero and make old outbox entries appear current. Use a fresh persisted binding token for each new profile and each URL change; retain missing-token legacy behavior only for trusted unchanged profiles.

2. Problem

Outbox records persist the session and command data, but no endpoint. Reconcile, cancel, switch, and submission checks use the outbox’s current client and reader. The composer also matches entries to server pending messages by `messageId`, so an old entry could claim a coincident ID from another endpoint.

A URL edit preserves profile and session identity, so endpoint equality alone fails for A→B→A. The live directory keys slots by profile ID and endpoint, and the route, workspace draft handoff, health checks, and tab warm cache also need binding-aware invalidation.

3. Objective

- Support local saved-profile name and URL edits, an independent persisted default, and wrapping Active/Default/supported-auth metadata.
- Keep launch-tab → saved-active → valid-default → first-profile restore priority. Setting or clearing Default must not switch the active server.
- Prevent any old binding’s outbox command from being replayed, correlated, cancelled, or switched on a new binding, including after restart and A→B→A.
- Preserve unchanged legacy reconciliation, fresh deliberate sends, local outbox entries, tabs, drafts, and workspace state.
- Route Settings search to the existing Servers page and focus/highlight its filter without changing `/hosts` URI handling for external links.

- Verified: outbox `_Record` has no endpoint. `_recover` turns persisted `sending` into `uncertain`; `_persist` already verifies exact readback after a thrown write. Reconciliation releases the queue during backoff.

5. Resolved Decisions

- Store optional `bindingRevision` on each profile as a bounded opaque token. Missing means pre-feature legacy binding. New profiles get a fresh token; every canonical URL change rotates it; label-only edits preserve it. It is neither `SessionRef` identity nor credential scope.
- Store both the validated full endpoint and binding token on every new outbox record. Compare both before network access. Legacy records with neither field are eligible only when a trusted production slot has the actual loaded profile with no binding token; an outbox without trusted profile context treats them as local-only.
- Reject a present malformed endpoint or binding field as unreadable; never reinterpret it as a legacy omission. Preserve the raw ledger and allow local inspection/dismissal.
- Do not move, copy, purge, probe, or require reading credentials for a metadata edit. Reuse the target’s existing origin/profile/type vault scope; credential operations validate the current binding and existing expected credential.
- Use `WorkspaceStore` as the sole default authority. Keep its v1 envelope and unknown fields; reconcile thrown writes inside its serialized queue before allowing later writes.
- Use a typed router extra while keeping the URI exactly `/hosts`. Add the filter label to Settings search matching; do not copy the Settings query into the server filter.

8. Risks and Mitigations

- **Stale command crosses binding:** an integer reset to zero is insufficient for same-ID recreation. Fresh per-profile tokens plus rotation on every URL change fence restart, A→B→A, and post-change recreation.
- **Legacy provenance is limited:** pre-feature outbox records have no endpoint, and the old profile record has no incarnation. The supported UI only mints random IDs and the profile API is create-only; retain legacy reconciliation only for a trusted loaded legacy profile. Raw profile-ID reuse before this change is indistinguishable from that supported history.
- **Async mutation completes during edit:** an already-started request can finish on its captured old endpoint. Revoke synchronously, prevent all later remote steps, persist only to its old-bound record, and ensure the new slot cannot correlate it.
- **Unknown storage outcomes:** exact readback distinguishes intended from unchanged state; unknown data blocks writes and stays preserved until read-only reconciliation.
- **Same-origin path retains vault credential by design:** path is excluded from existing vault scope. Outbox token still rotates, so old commands cannot use the new path binding.

9. Assumptions and Fallbacks

- The token is a bounded 128-bit opaque value generated with the existing secure-random approach; tests inject deterministic generators. Missing token means legacy only; new saves and URL edits always persist a token.
- Legacy records are network-eligible only in the production slot built from an actual loaded profile with no token. An outbox without that context, or a profile/outbox with malformed known fields, remains local-only and unreadable data is never overwritten.
- The historical store has no provenance to distinguish a raw same-ID rewrite before this change. The supported path does not expose profile IDs for reuse; if arbitrary manual metadata rewriting is in scope, legacy replay cannot be proven safe from existing data and must fail closed for that untrusted profile.
- A label-only edit does not read credentials or rotate binding. URL edits do not transfer credentials; serialized expected-binding checks ensure a credential repair either completes against its original binding or fails stale.
