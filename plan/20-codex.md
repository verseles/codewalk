## 0. Executive summary

1. **Use the Codex app-server v2 JSON-RPC protocol. It is the only surface built for rich clients.** [V]
   - The Codex VS Code extension, the ChatGPT desktop app (locally and over SSH), the Codex TUI itself, the official Python SDK, and the community ACP adapter `@agentclientprotocol/codex-acp` all drive it.
   - The protocol is bidirectional JSON-RPC 2.0 with the `"jsonrpc"` field omitted on the wire.
   - It covers threads, turns, and items, with streaming deltas, server→client approval requests, rate limits, models, skills, fuzzy file search, review, compaction, a PTY command API, and a filesystem API.
   - It is officially labelled **"experimental … not supported for production workloads"** and changes weekly. Every Codex release ships a matching generated schema.
2. **The "daemon" the user heard about is `codex app-server daemon`.** [V]
   - It is a managed, shared, background app-server per `CODEX_HOME`.
   - Since **v0.157.0 (2026-09-25)** the interactive TUI auto-starts it by default and attaches to it. The feature flag `daemon_auto_start` is stable and on.
   - It listens **only on a local Unix socket**: `$CODEX_HOME/app-server-control/app-server-control.sock`. That socket speaks **WebSocket over UDS** (HTTP Upgrade), has mode `0600`, and has no token auth.
   - It auto-updates itself on a schedule, independently of the CLI.
   - It is multi-client: the TUI, `codex agents`, `codex queue`, and any third-party client share live threads. Pending approvals are replayed to a client that re-joins a running thread.
3. **"Remote control" is not a third-party transport.** [V]
   - `codex remote-control …` makes the daemon dial **out** to OpenAI's relay at `wss://chatgpt.com/backend-api/wham/remote/control/server`, so the first-party ChatGPT mobile/desktop apps can control it after QR or manual pairing.
   - The URL allowlist accepts only `chatgpt.com` and `chatgpt-staging.com` hosts, plus localhost.
   - Official docs say it is "not a replacement for `codex app-server --listen` when you're building a local protocol client".
4. **Remote access for a phone needs a transport or bridge that CodeWalk owns.** Three options, best first:
   - **(A) SSH → shared daemon** [V for the building blocks]. Run `codex app-server daemon start` (idempotent, prints JSON), then `codex app-server proxy` (a raw stdio↔UDS byte pipe). CodeWalk then speaks WebSocket over the SSH channel. Turns keep running on the host if the phone drops, and the session is shared with the user's TUI.
   - **(B) Dedicated TCP WebSocket listener** [V]: `codex app-server --listen ws://IP:PORT --ws-auth capability-token --ws-token-file /abs/path`.
     - Non-loopback binds **refuse to start without auth** in 0.160.0.
     - There is no TLS built in, so put it behind Tailscale/WireGuard/SSH or a TLS proxy.
     - Any request carrying an `Origin` header gets **403**. A Flutter **web** build cannot connect directly; dart:io on mobile and desktop sends no Origin.
     - This is a separate process, not the shared daemon.
   - **(C) Thin host bridge** [U]: for example a small "codewalk-bridge" or Caddy that terminates TLS and auth and forwards to the daemon UDS. CodexMonitor and Happy each ship their own daemon or bridge.
5. **Feature coverage is very good.** It includes streaming text and reasoning, command output, diffs, plan/todo updates, approvals (accept, accept-for-session, decline, cancel, exec-policy amendment), and mid-turn steering. It also has token usage per thread, account rate limits (primary and secondary windows, plan type, credits, reset credits), models with reasoning efforts, skills, review, compaction, goals, subagents (child threads), a PTY terminal, and fs read/write/watch.
6. **Gaps:**
   - No file undo or snapshots: `/undo` was un-shipped, and `thread/rollback` was **removed in v0.156.0**.
   - No server-side slash-command or custom-prompt registry; custom prompts are deprecated in favour of skills.
   - Plan mode (`collaborationMode`), the queue, and per-thread settings updates require `experimentalApi`.
   - HTTP(S) image URLs are rejected; use data URLs.
   - `command/exec` PTY sessions die when the connection closes.
7. **Terms of service** [V for the quoted text; the legal reading is U]:
   - The app-server docs say: *"If you've built a local or open-source application using Codex app-server authentication, you can continue using it, though we recommend migrating to Sign in with ChatGPT … App-server authentication has never been permitted for commercial or hosted services."*
   - Reading: an open-source, self-hosted client that drives the user's own Codex install looks tolerated. A paid or hosted offering would need the SIWC partner program.

### 2.3 How it runs [V: source `codex-rs/app-server-daemon/src/backend/pid.rs`, `app-server-transport/src/transport/unix_socket.rs`]
- Launch args are `codex app-server --listen unix://`, with `--remote-control` added when enabled. A daemon **never opens a TCP port**.
- The socket path is `$CODEX_HOME/app-server-control/app-server-control.sock`. On this host it is a symlink to `/tmp/codex-daemon-<uid>/<hash>`. The directory is `0700` and the socket `0600`.
- Accept uses `tokio_tungstenite::accept_hdr_async_with_config`, so a WebSocket handshake is required even on the UDS.
- State lives in `$CODEX_HOME/app-server-daemon/`: `settings.json`, `app-server.pid`, `app-server-updater.pid`, `daemon.lock`.
  - Example `settings.json`: `{"remoteControlEnabled": false, "shutdownGraceSeconds": 60, "updater": {"autoUpdateEnabled": false, "updateIntervalMinutes": 120}}`
- Updates: an eligible managed daemon checks after 5 minutes, then hourly. **A version can differ from the user's CLI**; on this host the CLI is 0.159.3 and the daemon is 0.160.0. CodeWalk must negotiate against the daemon's protocol, not the CLI's.
- The daemon inherits the environment it was started with ("per-client environment isolation is not provided").
- Platforms: Linux, macOS, and Windows (Windows needs a non-elevated terminal that allows detached children; AF_UNIX path ≤108 bytes).

### 2.4 Multi-client semantics [V: source `app-server/src/lib.rs`, `request_processors/thread_lifecycle.rs`; docs]
- Every **initialized connection is auto-subscribed to every newly created thread**, including subagent threads. In `lib.rs` the `thread_created_rx` branch calls `try_attach_thread_listener` for all initialized connections.
  - So the client must route every notification by `threadId`. You will also see threads created by other clients, such as the TUI.
- Calling `thread/resume` on a running `threadId` makes the server **rejoin** that live thread. It replays token usage and goal state, then **replays pending server requests (approvals) to the connection** (`replay_requests_to_connection_for_thread`).
- After one client answers an approval, `serverRequest/resolved {threadId, requestId}` is broadcast so other clients can dismiss their prompt (v0.122.0 #15134).
- `thread/unsubscribe`: when the last subscriber leaves, the thread unloads after **30 minutes** without subscribers or activity, then emits `thread/closed`.
- `thread/loaded/list` returns thread ids currently in memory. Use it to show running sessions.

## 3. Protocol reference (app-server v2)

Full method list: `codex-src/methods.md`. Types: `codex-src/key-types.ts`. Unless noted otherwise, examples are **verbatim from the official doc page**. Examples marked **(schema-built)** were constructed from the generated 0.159.3 schema.

### 3.1 Framing and errors [V]
- Request: `{ "method": "...", "id": <int|string>, "params": {...} }`.
- Response: `{ "id": ..., "result": {...} }` or `{ "id": ..., "error": { "code": n, "message": "...", "data"?: ... } }`.
- Notification: `{ "method": "...", "params": {...} }`.
- **Server→client requests** have an `id` too, and the client MUST answer with the same `id`.
- Error codes (source `app-server/src/error_code.rs`):
  - `-32600` invalid request. Also returned for provider-requirement violations and for archiving a live internal worker.
  - `-32601` method not found. Also returned for unsupported features such as paginated thread creation.
  - `-32602` invalid params.
  - `-32603` internal.
  - **`-32001` "Server overloaded; retry later."** on bounded WebSocket ingress. Retry with exponential backoff and jitter.
  - The data code `"input_too_large"`.
- Experimental gating: sending an experimental method or field without opt-in gets the error `"<descriptor> requires experimentalApi capability"`.

### 3.2 Initialize handshake [V]
```json
{ "method": "initialize", "id": 0, "params": {
    "clientInfo": { "name": "codewalk", "title": "CodeWalk", "version": "1.265.0" },
    "capabilities": { "experimentalApi": true,
                      "optOutNotificationMethods": ["item/reasoning/textDelta"] } } }
{ "method": "initialized", "params": {} }
```
- `InitializeCapabilities` fields:
  - `experimentalApi: boolean`
  - `requestAttestation: boolean`
  - `explicitGatewayOauth?`
  - `mcpServerOpenaiFormElicitation?`
  - `optOutNotificationMethods?: string[]` (exact names only)
  - `extensions?`
- `InitializeResponse = { userAgent, codexHome, platformFamily: "unix"|"windows", platformOs: "macos"|"linux"|"windows" }`.
- Initialize **once per connection**. Earlier requests get `Not initialized`; a repeat gets `Already initialized`.
- The docs ask that `clientInfo.name` identify the integration to the OpenAI Compliance Logs Platform. Enterprise integrations should contact OpenAI to be added to a known-clients list. [V]
- The server version is not a dedicated field. Parse `userAgent` [U on format], or run `codex app-server daemon version` over SSH.

### 3.3 Threads [V]
- **Methods:** `thread/start`, `thread/resume`, `thread/fork`, `thread/read` (`includeTurns`), `thread/list`, `thread/turns/list`, `thread/items/list`, `thread/loaded/list`, `thread/name/set`, `thread/metadata/update` (pin, gitInfo), `thread/archive`, `thread/unarchive`, `thread/delete`, `thread/unsubscribe`, `thread/compact/start`, `thread/shellCommand`, `thread/inject_items`, `thread/goal/{set,get,clear}`, `thread/attachment/{add,list,remove}`, `thread/revert` (paginated threads only).
- **Experimental-only:** `thread/settings/update`, `thread/queue/{add,list,update,delete,reorder,start}`, `thread/search`, `thread/searchOccurrences`, `thread/backgroundTerminals/{list,terminate,clean}`, `thread/timeline/list`, `project/*`, `thread/memoryMode/set`, `thread/realtime/*`.
- **Notifications:** `thread/started`, `thread/status/changed`, `thread/archived`, `thread/unarchived`, `thread/deleted`, `thread/closed`, `thread/name/updated`, `thread/settings/updated`, `thread/goal/updated`, `thread/goal/cleared`, `thread/queue/changed`, `thread/tokenUsage/updated`, `thread/compacted` (deprecated; use the `contextCompaction` item).
- **`Thread` object** (key fields):
  - Identity and lineage: `id` (UUIDv7), `sessionId`, `forkedFromId`, `parentThreadId` (set when the thread is a subagent).
  - Display: `preview` (first user message), `name`.
  - Runtime: `status` (see below), `model`, `reasoningEffort`.
  - Origin and location: `cwd`, `cliVersion`, `source` (`"cli"|"vscode"|"exec"|"appServer"|{subAgent}|…`), `gitInfo`.
  - Timestamps: `createdAt`, `updatedAt`.
  - Subagent labels: `agentNickname`, `agentRole`.
  - `turns`, which is populated only on resume, fork, and read with turns.
  - `status` is `{type:"notLoaded"|"idle"|"systemError"}` or `{type:"active", activeFlags:["waitingOnApproval"|"waitingOnUserInput"]}`. This is good for "needs attention" badges and push notifications.
- **Threads created via `codex app-server` are recorded with `source: "vscode"`.** The CLI passes `SessionSource::VSCode`. TUI threads are `cli`. `thread/list` defaults to `sourceKinds` `cli` + `vscode`, so both appear. Pass `sourceKinds` explicitly to include `exec`, `appServer`, or `subAgent*`. [V source]

**Pitfalls** [V source `app-server-protocol/src/protocol/v2/shared.rs`]:
- The official docs examples use `"approvalPolicy": "never"`/`"unlessTrusted"` and `"sandbox": "workspaceWrite"`. On the wire:
  - `AskForApproval` = `"untrusted" | "on-request" | "never" | {"granular":{…}}` (granular is experimental).
  - `SandboxMode` (in `thread/start.sandbox`) = `"read-only" | "workspace-write" | "danger-full-access"`.
  - `turn/start.sandboxPolicy` is an *object*: `{"type":"dangerFullAccess"} | {"type":"readOnly","networkAccess":bool} | {"type":"workspaceWrite","writableRoots":[…],"networkAccess":bool,"excludeTmpdirEnvVar":bool,"excludeSlashTmp":bool} | {"type":"externalSandbox","networkAccess":"restricted"|"enabled"}`.
  - Happy's migration notes record the same lesson.
- Docs say `untrusted` is "no longer supported as a selectable approval policy". UI presets should use only `on-request` and `never`.

### 3.4 Turns: start, steer, interrupt [V]
`UserInput` union:
- `{"type":"text","text","text_elements":[{byteRange,placeholder}]}`
- `{"type":"image","url"|"fileId","detail"?: "auto"|"low"|"high"|"original"}`
- `{"type":"localImage","path"}`
- `{"type":"audio","url"}`
- `{"type":"localAudio","path"}`
- `{"type":"skill","name","path"}`
- `{"type":"mention","name","path"}`. Mention is for structured targets like `app://<connector-id>` or `plugin://<name>@<marketplace>`, not files (source `protocol/src/user_input.rs`).

```json
{ "method": "turn/start", "id": 30, "params": {
  "threadId": "thr_123",
  "input": [ { "type": "text", "text": "Run tests", "text_elements": [] },
             { "type": "image", "url": "data:image/png;base64,iVBORw0KGgo..." } ],
  "model": "gpt-6.1-sol", "effort": "medium", "summary": "concise",
  "approvalPolicy": "on-request",
  "sandboxPolicy": { "type": "workspaceWrite", "writableRoots": ["/Users/me/project"], "networkAccess": true,
                     "excludeTmpdirEnvVar": false, "excludeSlashTmp": false } } }
{ "id": 30, "result": { "turn": { "id": "turn_456", "status": "inProgress", "items": [], "error": null } } }
```
- Per-turn overrides (model, effort, summary, cwd, approvalPolicy, sandboxPolicy) **persist for later turns** on the thread. `outputSchema` applies to one turn only.
- **Images: HTTP(S) image URLs are rejected** at `turn/start` and `turn/steer` ingress (PR #29419, v0.142). **Inline `data:` URLs and `localImage` (a host path) are accepted.** [V] Check `model.inputModalities` before offering images.
- **`turn/start` on a thread that already has an active turn *steers* that turn.** It returns the active turn id and emits no new `turn/started`. [V source `turn_processor.rs` `start_or_steer_turn`]
- Explicit steer:
```json
{ "method": "turn/steer", "id": 32, "params": { "threadId": "thr_123",
  "input": [ { "type": "text", "text": "Actually focus on failing tests first.", "text_elements": [] } ],
  "expectedTurnId": "turn_456" } }
{ "id": 32, "result": { "turnId": "turn_456" } }
```
- Steer errors:
  - "no active turn to steer"
  - "expected active turn id `X` but found `Y`"
  - `codexErrorInfo: {"activeTurnNotSteerable":{"turnKind":"review"|"compact"}}`
  - "active turn uses a different output schema"
- Interrupt:
```json
{ "method": "turn/interrupt", "id": 31, "params": { "threadId": "thr_123", "turnId": "turn_456" } }
{ "id": 31, "result": {} }   // then turn/completed with turn.status = "interrupted"
```
- Queue-for-next-turn (experimental): `thread/queue/add {threadId, input, clientUserMessageId}`, then `thread/queue/list|update|delete|reorder|start`, with the notification `thread/queue/changed`.
- Experimental `turn/settings/update {threadId, turnId, model?, effort?, summary?, serviceTier?, approvalsReviewer?}` changes the **running** turn only.
- Skill invocation (docs): put `$skill-name` in the text **and** add `{ "type": "skill", "name": "skill-creator", "path": "/Users/me/.codex/skills/skill-creator/SKILL.md" }`.
- `toolOutput` turns: `input: []` plus `toolOutput: {name, namespace, output}`.

### 3.7 Errors [V]
- On failure the server emits `error { error: TurnError, willRetry: bool, threadId, turnId }`. If `willRetry` is false, a `turn/completed` with `status:"failed"` follows.
- `TurnError = { message, codexErrorInfo, additionalDetails, misalignment }`.
- `CodexErrorInfo` values (camelCase on the wire): `contextWindowExceeded`, `sessionBudgetExceeded`, `usageLimitExceeded`, `rateLimitExceeded`, `flexUnavailable`, `serverOverloaded`, `cyberPolicy`, `misalignmentPolicyViolation`, `tooManyDenials`, `{httpConnectionFailed:{httpStatusCode}}`, `{responseStreamConnectionFailed:{…}}`, `internalServerError`, `unauthorized`, `badRequest`, `threadRollbackFailed`, `sandboxError`, `{responseStreamDisconnected:{…}}`, `{responseTooManyFailedAttempts:{…}}`, `{activeTurnNotSteerable:{turnKind}}`, `other`.
- The docs list PascalCase names (`ContextWindowExceeded`, …), but **the 0.159.3 schema serializes them in camelCase**.

### 3.9 Auth [V]
- `account/read {refreshToken?}` returns `{ account: {type:"apiKey"} | {type:"chatgpt", email, planType} | {type:"amazonBedrock",…} | null, requiresOpenaiAuth, workspaceRouting }`.
- `account/login/start` variants:
  - `{type:"apiKey", apiKey}`
  - `{type:"chatgpt", useHostedLoginSuccessPage?, appBrand?}` returns `{loginId, authUrl}`. The callback is **`http://localhost:<port>` on the host**, so it is unusable from a phone unless port-forwarded.
  - **`{type:"chatgptDeviceCode"}`** returns `{loginId, verificationUrl:"https://auth.openai.com/codex/device", userCode:"ABCD-1234"}`. **This is the remote-friendly flow.** It is in beta and the user must enable device-code login in ChatGPT security settings or workspace permissions [V `auth.md`].
  - `{type:"chatgptAuthTokens", accessToken, chatgptAccountId, chatgptPlanType?}` (experimental; the host app owns refresh via server request `account/chatgptAuthTokens/refresh`)
  - Bedrock variants
- Notifications: `account/login/completed {loginId, success, error}` and `account/updated {authMode, planType}`. `authMode` is one of `apikey|chatgpt|chatgptAuthTokens|headers|agentIdentity|personalAccessToken|bedrockApiKey|bedrockAccessKeys|null`.
- Other methods: `account/login/cancel {loginId}`, `account/logout`.
- Credentials live on the **host** (`~/.codex/auth.json` or the keyring). The phone never needs them when the user already ran `codex login` on the host.

### 3.10 Models, effort, modes, personality [V]
- **Models:** `model/list {cursor?, limit?, includeHidden?}` returns `Model { id, model, displayName, description, hidden, isDefault, supportedReasoningEfforts:[{reasoningEffort, description}], defaultReasoningEffort, inputModalities: ["text"|"image"|"audio"], serviceTiers, defaultServiceTier, upgrade, upgradeInfo, multiAgentVersion, supportsPersonality (always false now) }`.
- **Reasoning effort:** `ReasoningEffort` is a **string** (open set). Docs mention `"ultra"` as the setting for proactive multi-agent behaviour. Always render from `supportedReasoningEfforts`.
- **Reasoning summary:** `auto|concise|detailed|none`.
- **Collaboration modes** (experimental): `collaborationMode/list` returns `[{name, mode: "plan"|"default", model, reasoning_effort}]`. Apply with `turn/start.collaborationMode = {mode, settings:{model, reasoning_effort, developer_instructions: null}}` (the field is experimental). Plan mode streams `plan` items via `item/plan/delta`.
- **Personality:** `"friendly"/"pragmatic"` are **deprecated no-ops**, `"none"` strips the `# Personality` section, and `features.personality` is ignored.
- **Fast mode:** service tiers via `serviceTier` / `serviceTierForTurn`.

### 3.11 Skills, slash commands, prompts, @-mentions [V]
- **Skills:** `skills/list {cwds?, forceReload?, perCwdExtraUserRoots?}` returns `[{cwd, skills:[{name, description, shortDescription?, interface?{displayName, shortDescription,…}, dependencies?, path, scope: user|repo|system|admin, enabled, pluginId}], errors}]`. Related: `skills/config/write {path, enabled}`, the notification `skills/changed`, and `skills/extraRoots/set`. Invoke with `$name` text plus a `skill` input item.
- **Slash commands:** these are **TUI-side only**; the protocol has no command registry. CodeWalk must implement its own palette by mapping commands to RPCs (see the mapping table). The TUI list is in `doc` §"Built-in slash commands": `/model /fast /plan /goal /permissions /review /compact /diff /mention /new /resume /fork /rename /status /usage /mcp /skills /agent /ps /stop /init /side …`.
- **Custom prompts** (`~/.codex/prompts/*.md` as `/prompts:name`): **deprecated** in favour of skills and **not exposed** in the app-server schema.
- **@ file mentions:**
  - `fuzzyFileSearch {query, roots: string[], cancellationToken: string|null}` returns `{files:[{root, path, match_type: "file"|"directory", file_name, score, indices}]}` (stable).
  - Experimental session variant: `fuzzyFileSearch/sessionStart|sessionUpdate|sessionStop`, with notifications `fuzzyFileSearch/sessionUpdated|sessionCompleted`.
  - The selected file is inserted as path text, optionally with `text_elements` for chip rendering [U for TUI parity].
  - `mention` items are for `app://` and `plugin://` targets.

### 3.12 Undo, redo, snapshots, rewind [V]
- **File undo or snapshot:** none. `/undo` (ghost commits) was "un-shipped" (#8424). The protocol has no file-revert API.
- **Conversation rewind:**
  - `thread/rollback` was **removed in v0.156.0** (#44915). It is absent from the 0.159.3 schema, although the docs page still lists it.
  - `thread/revert {threadId, beforeTurnId}` works only for **paginated** threads, which current servers cannot create yet ("Paginated thread creation isn't supported yet and returns -32601").
  - The practical primitive is **`thread/fork {threadId, beforeTurnId | lastTurnId}`**, which yields a new thread id.
- **File-level revert options** [U, client-implemented]:
  - Show `turn/diff/updated` and offer a git-based revert through `command/exec` (for example `git apply -R` of the turn diff), or `git stash`/checkout.
  - The CLI has `codex apply` (applies the latest diff) but no reverse.

### 3.13 Review, compaction, goals, background work [V]
- **Review:** `review/start {threadId, target: {type:"uncommittedChanges"} | {type:"baseBranch",branch} | {type:"commit",sha,title} | {type:"custom",instructions}, delivery?: "inline"|"detached"(deprecated)}` returns `{turn, reviewThreadId}`. It emits `enteredReviewMode` and `exitedReviewMode` items, and review turns cannot be steered.
- **Compaction:** `thread/compact/start {threadId}` returns `{}`. Progress arrives via `turn/*` and a `contextCompaction` item.
- **Goals** (`/goal`): `thread/goal/set {threadId, objective(≤4000 chars), status, tokenBudget}` with statuses `active|paused|blocked|usageLimited|budgetLimited|complete`. Codex continues automatically toward the goal. This is the closest thing to "background tasks"; saved goals recover after daemon restarts (v0.155).
- **Background terminals** (experimental): `thread/backgroundTerminals/list|terminate|clean`.

### 3.14 Subagents and multi-agent [V]
- The agent spawns child **threads**:
  - A `collabAgentToolCall` item (`spawnAgent`, `wait`, …) appears in the parent.
  - Children have `parentThreadId`, `source: {subAgent:{thread_spawn:{parent_thread_id, depth, agent_nickname, agent_role}}}`, `agentNickname`, and `agentRole`.
  - `subAgentActivity` items track them.
- Clients are auto-subscribed to new child threads (§2.4), so approvals from children arrive with the **child's `threadId`**.
- List children with `thread/list {parentThreadId}` or `{ancestorThreadId}` (experimental filters).
- **Direct input to v2 sub-agents is rejected** (#27173). `Thread.canAcceptDirectInput` (experimental field) tells the client.
- `thread/archive` and `thread/delete` cascade to spawned descendants.
- Config: `[agents] max_concurrent_threads_per_session, default_subagent_model, default_subagent_reasoning_effort`. Proactive multi-agent behaviour is tied to `effort: "ultra"` (`multiAgentMode` is deprecated and ignored).

### 3.15 Terminal, command exec, filesystem [V]
- **`command/exec`** runs a standalone command (an argv array) **under the sandbox**. Params: `processId`, `tty`, `streamStdin`, `streamStdoutStderr`, `size {rows, cols}`, `cwd`, `env`, `timeoutMs` | `disableTimeout`, `outputBytesCap`, `sandboxPolicy` | `permissionProfile`. The response `{exitCode, stdout, stderr}` is deferred until exit.
  - Streaming: `command/exec/outputDelta {processId, stream, deltaBase64, capReached}`.
  - Control: `command/exec/write {processId, deltaBase64?, closeStdin?}`, `command/exec/resize {processId, size}`, `command/exec/terminate {processId}`.
  - **These sessions are connection-scoped: if the connection closes, the server kills the process.**
```json
{ "method": "command/exec", "id": 50, "params": { "command": ["bash","-l"], "processId": "term-1", "tty": true,
  "size": { "rows": 40, "cols": 120 }, "cwd": "/Users/me/project", "sandboxPolicy": { "type": "dangerFullAccess" }, "disableTimeout": true } }
```
- **`thread/shellCommand {threadId, command, timeoutMs?}`** is a user `!cmd` that runs **unsandboxed with full access** and is injected into the thread transcript.
- **`process/spawn|writeStdin|resizePty|kill`** (experimental) is unsandboxed explicit process control, with notifications `process/outputDelta` and `process/exited`.
- **Filesystem** (absolute host paths, base64): `fs/readFile {path}` returns `{dataBase64}`, `fs/writeFile {path, dataBase64}`, plus `fs/readDirectory`, `fs/getMetadata`, `fs/createDirectory`, `fs/remove`, `fs/copy`, and `fs/watch {watchId, path}` / `fs/unwatch` with the `fs/changed` notification. These cover file browsing and attachment upload, for example writing a picked file to the host and then referencing its path.

### 3.16 Config, MCP, misc [V]
- **Config:** `config/read`, `config/value/write`, `config/batchWrite` (they write the user's `config.toml`), plus `configRequirements/read` and `experimentalFeature/list|enablement/set`.
- **MCP:** `mcpServerStatus/list {detail:"full"|"toolsAndAuthOnly", serverName?, threadId?}`, `mcpServer/oauth/login` (returns an HTTPS URL), `config/mcpServer/reload`, `mcpServer/resource/read`, `mcpServer/tool/call`. ## 4. Remote access story

### 4.1 What Codex offers [V]
| Mode | Network exposure | Auth | Shares the daemon? | Notes |
|---|---|---|---|---|
| `--listen stdio://` (default) | none | process ownership | no (one process per connection) | The stdio app-server **exits when its connection closes** (#36035). Over SSH, a dropped phone connection kills running turns. |
| `--listen unix://[PATH]` (the daemon uses this) | local UDS `0600` | filesystem permissions | yes, when it is the daemon socket | WebSocket handshake over the UDS |
| `--listen ws://127.0.0.1:PORT` | loopback TCP | optional | no (separate process) | Docs: appropriate "for localhost and SSH port-forwarding workflows" |
| `--listen ws://0.0.0.0:PORT --ws-auth capability-token --ws-token-file /abs` (or `--ws-token-sha256 HEX`) | LAN/VPN TCP | `Authorization: Bearer <token>` on the upgrade, SHA-256 compared in constant time | no | **0.160.0 refuses non-loopback binds without `--ws-auth`.** The docs page still says "allow unauthenticated connections by default during rollout", which is stale. Auth is checked only at upgrade; there is no expiry or revocation afterwards. |
| `--ws-auth signed-bearer-token --ws-shared-secret-file /abs [--ws-issuer --ws-audience --ws-max-clock-skew-seconds]` | same | HS256 JWT (secret ≥32 bytes), `exp` required, `nbf`/`iss`/`aud` optional | no | Good for short-lived tokens minted by a bridge |
| Health | — | — | — | `GET /readyz`, `GET /healthz` (200). **Any request with an `Origin` header → 403**, so browsers and Flutter web are blocked. |
| TLS | — | — | — | **Not built in.** "use TLS termination or a secure proxy when clients connect with `wss://`" |
| Remote control | outbound to OpenAI relay | ChatGPT account and device pairing | yes | First-party only (§0.3) |

Official guidance [V `remote-connections.md`]: *"Don't expose app-server transports directly on a shared or public network. If you need to reach a remote machine outside your current network, use a VPN or mesh networking tool instead of exposing the app server directly to the internet."* The `codex --remote` docs say: *"Use plain WebSockets only for localhost or an SSH port-forwarded connection."*

### 4.2 Options for CodeWalk
- **A. SSH plus the shared daemon (closest to the official ChatGPT-desktop SSH flow).**
  1. Exec `codex app-server daemon start` and parse its JSON.
  2. Open a channel running `codex app-server proxy`. It pipes raw bytes, so the client must perform the WebSocket client handshake over the channel.
  3. Practical Dart route [U]: a loopback `ServerSocket` on the phone pipes into the SSH channel, then `WebSocket.connect('ws://127.0.0.1:<p>')`. Or implement WS framing directly. Alternatively, use dartssh2 Unix-socket forwarding (`direct-streamlocal`) if supported [U].
  - Pros: no open port and no token management (SSH keys); a **shared live session** with the TUI; turns survive phone disconnects; pending approvals replay on rejoin; `daemon bootstrap` exists "for SSH-driven use".
  - Cons: CodeWalk needs an SSH client stack; the host needs sshd; Windows hosts need OpenSSH.
- **B. Dedicated WS listener** (simplest client code, since CodeWalk already speaks network protocols to OpenCode).
  - Run `codex app-server --listen ws://<tailscale-ip>:4500 --ws-auth capability-token --ws-token-file ~/.codex/codewalk-token`, kept alive by systemd, launchd, or tmux.
  - The phone connects via `WebSocket.connect(url, headers: {'Authorization': 'Bearer …'})` [V: dart:io sends no Origin by default; source `sdk/lib/_http/websocket_impl.dart`]. Use Tailscale/WireGuard or a TLS proxy.
  - Cons: a separate process from the TUI daemon, so no live sharing with TUI sessions. Two app-server processes touching the same `CODEX_HOME` thread concurrently is risky [U]. Codex docs label it unsupported. The user must manage the process and token.
- **C. CodeWalk host bridge** [U].
  - A small companion (Go, Rust, or Dart) on the host exposes `wss://` with CodeWalk auth or pairing and forwards frames to the daemon UDS. Most of the protocol passes through untouched.
  - It could also add push-notification hooks (`thread/status/changed` → waitingOnApproval) and survive app backgrounding.
  - This mirrors CodexMonitor's `codex_monitor_daemon` (TCP plus token over Tailscale) and Happy's `happy-cli` (relay through Happy Server to `codex app-server` stdio).
  - A Caddy or nginx reverse proxy to the unix socket might work with zero code, because the UDS speaks HTTP/WebSocket [U, untested; the daemon socket path is a symlink into `/tmp/codex-daemon-<uid>/`].

### 4.3 Connection resilience notes
- On reconnect: `initialize`, then `thread/loaded/list`, then `thread/resume {threadId, excludeTurns:true}` for each visible thread. Pending approvals are replayed [V]. Use `thread/turns/list` to backfill.
- Item ids are stable, so dedupe deltas by `itemId` and treat `item/completed` as authoritative.
- The client must apply backoff on `-32001`.

### 4.4 How existing third-party clients connect [V]
- **Happy** (slopus/happy, 24k★):
  - Topology: mobile app → Happy Server (relay) → `happy-cli` on the host, which spawns `codex app-server --listen stdio://` per session.
  - It migrated from `codex mcp-server` because of model-change context loss, hanging cancels, and session-id confusion.
  - Its notes document wire gotchas: `result.thread.id`, flat `{type:"text",text}`, camelCase sandboxPolicy objects, decisions `accept|decline|cancel`, and empty model string = error.
- **CodexMonitor** (Dimillian/CodexMonitor, Tauri): one `codex app-server` per workspace, plus an optional "remote backend daemon" (TCP plus token, Tailscale helper) for iOS.
- **codex-acp** (`@agentclientprotocol/codex-acp`, TypeScript): a stdio ACP server that "starts the Codex App Server, translates ACP requests into Codex operations". Its source is a good reference for event and permission mapping, including native ACP subagent sessions, background terminals, and goals.
- **First-party:**
  - ChatGPT desktop drives remote hosts by starting "the remote Codex app server through SSH" (it requires `codex` on the remote `PATH`).
  - ChatGPT mobile uses the remote-control relay.
  - The TUI uses `--remote ws://|wss://|unix://`.

## 5. Install, update, headless [V]
- **Standalone installer** (macOS/Linux): `curl -fsSL https://chatgpt.com/codex/install.sh | sh`. Windows: `powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"`. Re-run either command to update.
- **npm:** `npm install -g @openai/codex` (latest 0.160.0). Platform builds come via optionalDependencies: `linux-x64`, **`linux-arm64`**, `darwin-x64`, `darwin-arm64`, `win32-x64`, `win32-arm64`.
- **Homebrew:** `brew install --cask codex` / `brew upgrade --cask codex`.
- **GitHub release assets** (rust-v0.160.0) are **musl static Linux** builds for `x86_64` and `aarch64` (GNU Linux builds stopped in v0.128), plus macOS arm64/x64 (`.tar.gz`, `.dmg`) and Windows x64/arm64.
  - There is also a **standalone `codex-app-server-<target>` binary** and a `codex-app-server-package-<target>` per target.
- **Self-update:** `codex update`; `codex app-server daemon update [-y]` for the daemon package (`CODEX_HOME/packages/app-server-daemon/current/bin/codex`). The daemon also auto-updates when the latest-channel installer was used.
- **Headless:**
  - `codex login --device-auth`, or pipe an API key with `printenv OPENAI_API_KEY | codex login --with-api-key`. Over the protocol, use `chatgptDeviceCode`.
  - Fresh-host bootstrap: `$HOME/.codex/packages/standalone/current/codex app-server daemon bootstrap [--remote-control]`.
  - Diagnostics: `codex doctor`.
  - The daemon keeps running after the TUI exits. The 30-minute idle unload applies only to threads.
- **Protocol drift:** the protocol changes almost every release (weekly stable, near-daily alphas). Ship CodeWalk against `generate-json-schema` output, tolerate unknown fields and variants, and detect the version at connect time.

## 8. Implementation pitfalls checklist (for planners)
1. **Version skew.** The daemon auto-updates (on this host CLI 0.159.3 vs daemon 0.160.0). Parse leniently: ignore unknown notifications, item `type`s, and enum values. Treat `ReasoningEffort` and `ThreadSource` as open strings.
2. **Experimental opt-in is all-or-nothing per connection.** Setting `experimentalApi:true` unlocks the queue, plan mode, `availableDecisions`, and settings updates, but those can change without notice. Gate them behind feature detection by catching "requires experimentalApi capability" and `-32601`.
3. **Wire enums differ from the docs examples.** See §3.3: `on-request`, `workspace-write`, and camelCase `sandboxPolicy` objects. Never send an empty `model` string.
4. **Route everything by `threadId`.** The client receives events for all new threads on the server, including the user's TUI threads and subagents.
5. **Approvals are JSON-RPC requests with ids.** Keep a pending map. Expect replays after `thread/resume`, and dismiss on `serverRequest/resolved`.
6. **`command/exec` PTYs die on disconnect.** For a mobile terminal, consider `thread/shellCommand` (transcripted) or a bridge that holds the connection.
7. **Images:** use base64 data URLs. Large payloads count toward WS frames; the `input_too_large` error exists.
8. **No Origin header** may reach the TCP listener. Flutter web needs a bridge.
9. **WS auth is checked only at upgrade**, with no in-band re-auth. Rotate tokens by restarting the listener.
10. **Rewind uses fork**, so the UI must handle "rewind creates a new session" (similar to the OpenCode fork/revert UX, but without file revert).
