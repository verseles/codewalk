## TL;DR

- **Exists, official, open source (MIT), just reached 1.0.0 (2026-10-01).** [V]
- **Best programmatic surface: RPC mode** — `pi --mode rpc`, a long-lived child process speaking strict
  JSONL over stdin/stdout (commands → `response` records + streamed session events + an extension-UI
  request/response sub-protocol). Documented, typed (`rpc-types.ts`), with an official TypeScript `RpcClient`. [V]
- **No network listener.** A phone client needs a thin host-side bridge (stdio ↔ WebSocket/SSE + auth +
  process supervision). An experimental CBOR/Unix-socket "pi-server/pi-protocol/pi-client" stack exists
  but is explicitly "experimental and has no compatibility guarantees". [V]
- **No ACP natively.** Community adapter `pi-acp` (svkozak, MIT, 0.0.34, listed in the official ACP registry) bridges ACP ↔ `pi --mode rpc`. [V]
- **No built-in permission system** ("YOLO" by design); approvals/questions/todos/subagents are extension territory. [V]
- Verdict: **Integrable, medium effort, low–medium risk** via RPC through a bridge. Richest wins:
  steer/follow-up queueing, session tree (fork/clone/entries cursor), thinking levels `off…max`, per-session cost stats.

## 3. RPC protocol detail (verbatim names)

### 3.1 Framing and lifecycle [V] (docs/rpc.md)

- One JSON object per line, **LF only**; strip optional preceding CR. Do **not** split on U+2028/U+2029
  (Node `readline` is non-compliant). Dart: split bytes on `0x0A`, then UTF-8 decode.
- stdout = protocol records only; stderr = diagnostics. Read stdout continuously (backpressure can stall Pi).
- Commands accept optional string `id`; the matching `response` repeats it. Handling is async → correlate by id.
- Session events carry no id (exception: `bash_execution_update` repeats the originating `bash` command id).
- Malformed JSON → `{"type":"response","command":"parse","success":false,"error":"Failed to parse command: …"}`.
- Shutdown: close child stdin. A successful `prompt` response only means accepted/queued/handled — wait for
  **`agent_settled`** (not `agent_end`) to know Pi will not continue (retries, compaction, queued messages).
- `RpcClient.promptAndWait()`; subscribe to events *before* sending `prompt`.

```json
{"id":"req-1","type":"get_state"}
{"id":"req-1","type":"response","command":"get_state","success":true,"data":{"model":{...},"thinkingLevel":"medium","isStreaming":false,"isCompacting":false,"steeringMode":"all","followUpMode":"one-at-a-time","sessionFile":"/path/to/session.jsonl","sessionId":"abc123","sessionName":"my-feature-work","autoCompactionEnabled":true,"messageCount":5,"pendingMessageCount":0}}
{"id":"req-3","type":"response","command":"set_model","success":false,"error":"Model not found: invalid/model"}
```

### 3.2 Complete command list (from `rpc-types.ts`, v1.0.0) [V]

Prompting/queue: `prompt` {message, images?, streamingBehavior?: "steer"|"followUp"} · `steer` {message, images?} ·
`follow_up` {message, images?} · `abort` · `clear_queue` (returns `{steering:[…], followUp:[…]}`) ·
`set_steering_mode` {mode:"all"|"one-at-a-time"} · `set_follow_up_mode` {mode}.
Session: `new_session` {parentSession?} → `{cancelled}` · `switch_session` {sessionPath} · `fork` {entryId} →
`{text, cancelled}` · `clone` · `get_fork_messages` → `[{entryId,text}]` · `get_entries` {since?} → `{entries, leafId}`
(durable cursor, includes pre-compaction history and abandoned branches) · `get_tree` → `{tree:[{entry,children,label?}], leafId}` ·
`get_messages` · `get_last_assistant_text` · `set_session_name` {name} · `get_session_stats` · `export_html` {outputPath?} · `get_state`.
Model/thinking: `set_model` {provider, modelId} · `cycle_model` · `get_available_models` ·
`set_thinking_level` {level} · `cycle_thinking_level` · `get_available_thinking_levels`.
Compaction/retry: `compact` {customInstructions?} · `set_auto_compaction` {enabled} · `set_auto_retry` {enabled} · `abort_retry`.
Shell: `bash` {command, excludeFromContext?} · `abort_bash`.
Discovery: `get_commands` (extension commands, prompt templates, skills — **not** built-in TUI commands).
Extension UI reply: `extension_ui_response` {id, value | confirmed | cancelled:true}.

**Not present:** no `list_sessions`, no `delete_session`, no in-file tree navigation (TUI `/tree` only), no file
search, no permission reply (no permission system), no model "agents".

Key payloads:

```json
{"id":"req-2","type":"prompt","message":"Review this repository"}
{"id":"req-2","type":"response","command":"prompt","success":true,"data":{"disposition":"started"}}
{"type":"prompt","message":"What's in this image?","images":[{"type":"image","data":"<base64>","mimeType":"image/png"}]}
{"type":"prompt","message":"New instruction","streamingBehavior":"steer"}
```

`data.disposition`: `"started"` | `"queued"` | `"handled"` (extension command or input handler consumed it → no run,
don't wait for `agent_settled`). If streaming and no `streamingBehavior` → error. Extension commands (`/mycommand`)
run immediately even while streaming; `/skill:name` and `/template` are expanded before sending.
Thinking levels: `"off"`, `"minimal"`, `"low"`, `"medium"`, `"high"`, `"xhigh"`, `"max"` (xhigh/max only when the model supports them).

```json
{"type":"response","command":"get_session_stats","success":true,"data":{"sessionFile":"/path/to/session.jsonl","sessionId":"abc123","userMessages":5,"assistantMessages":5,"toolCalls":12,"toolResults":12,"totalMessages":22,"tokens":{"input":50000,"output":10000,"cacheRead":40000,"cacheWrite":5000,"total":105000},"cost":0.45,"contextUsage":{"tokens":60000,"contextWindow":200000,"percent":30}}}
{"id":"req-1","type":"bash","command":"ls -la"}
{"type":"bash_execution_update","id":"req-1","delta":"total 48\n"}
{"id":"req-1","type":"response","command":"bash","success":true,"data":{"output":"total 48\n...","exitCode":0,"cancelled":false,"truncated":false}}
```

Model object (from `get_available_models`/`set_model`): `{id,name,api,provider,baseUrl,reasoning,input:["text","image"],contextWindow,maxTokens,cost:{input,output,cacheRead,cacheWrite}}` ($/Mtok).
`get_commands` row: `{name, description?, source:"extension"|"prompt"|"skill", sourceInfo:{path,source,scope:"user"|"project"|"temporary",origin,baseDir?}}`.

### 3.3 Event stream (shared by JSON and RPC modes) [V] (docs/json.md)

```json
{"type":"agent_start"}
{"type":"turn_start"}
{"type":"message_start","message":{"role":"user","content":"Review this repository","timestamp":1733234401000}}
{"type":"message_end","message":{...}}
{"type":"message_start","message":{"role":"assistant","content":[],"stopReason":"pending"}}
{"type":"message_update","usage":{"input":100,"output":1,"cacheRead":0,"cacheWrite":0,"totalTokens":101,"cost":{"input":0,"output":0,"cacheRead":0,"cacheWrite":0,"total":0}},"assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello "}}
{"type":"message_end","message":{"role":"assistant",...}}
{"type":"turn_end","message":{...},"toolResults":[]}
{"type":"agent_end","messages":[...],"willRetry":false}
{"type":"agent_settled"}
```

- Agent/turn: `agent_start`, `agent_end` {messages, willRetry}, `agent_settled`, `turn_start`, `turn_end` {message, toolResults}.
- Message: `message_start`, `message_update` {usage, assistantMessageEvent}, `message_end` (authoritative final message).
  `assistantMessageEvent.type`: `start`, `text_start|text_delta|text_end`, `thinking_start|thinking_delta|thinking_end`,
  `toolcall_start` {id, toolName}, `toolcall_delta`, `toolcall_end` {toolCall}, `done`, `error`. Wire deltas are delta-only
  (no cumulative `partial`); replace with `*_end` content and `message_end.message`.
- Tools: `tool_execution_start` {toolCallId, toolName, args}, `tool_execution_update` {…, partialResult},
  `tool_execution_end` {…, result:{content,details}, isError}. Nested calls (from codemode/`ctx.executeTool`) carry `parentToolCallId`, ids `<parent>/<n>`.
- Queue/state: `queue_update` {steering, followUp} (complete current queues), `entry_appended`, `session_info_changed` {name?}, `thinking_level_changed` {level}.
- Compaction: `compaction_start` {reason:"manual"|"threshold"|"overflow"}, `compaction_end` {reason, result?, aborted, willRetry, errorMessage?}.
- Retry: `auto_retry_start` {attempt, maxAttempts, delayMs, errorMessage:"529 overloaded"}, `auto_retry_end` {success, attempt, finalError?};
  `summarization_retry_scheduled|_attempt_start|_finished`.
- RPC-only: `bash_execution_update`, `extension_error` {extensionPath, event, error}.

### 3.4 Extension UI sub-protocol (how approvals/questions can work) [V] (docs/rpc-extension-ui.md)

Dialogs (block until answered): `select` {title, options[], timeout?}, `confirm` {title, message, timeout?}, `input` {title, placeholder?}, `editor` {title, prefill?}.
Fire-and-forget: `notify` {message, notifyType:"info"|"warning"|"error"}, `setStatus` {statusKey, statusText?}, `setWidget` {widgetKey, widgetLines?, widgetPlacement:"aboveEditor"|"belowEditor"}, `setTitle`, `set_editor_text` {text}.

```json
{"type":"extension_ui_request","id":"uuid-1","method":"select","title":"Allow dangerous command?","options":["Allow","Block"],"timeout":10000}
{"type":"extension_ui_response","id":"uuid-1","value":"Allow"}
{"type":"extension_ui_response","id":"uuid-2","confirmed":true}
{"type":"extension_ui_response","id":"uuid-3","cancelled":true}
```

Permission gating pattern (official docs, extensions.md): an extension handles `tool_call` and can block:

```ts
pi.on("tool_call", async (event, ctx) => {
  const hints = pi.getAllTools().find((t) => t.name === event.toolName)?.annotations;
  const needsApproval = hints?.destructiveHint === true ||
    (!hints?.readOnlyHint && ((hints?.destructiveHint ?? true) || (hints?.openWorldHint ?? true)));
  if (needsApproval && !(await ctx.ui.confirm("Allow tool call?", event.toolName))) {
    return { block: true, reason: `${event.toolName} was not approved` };
  }
});
```

In RPC mode `ctx.ui.confirm` becomes an `extension_ui_request` → CodeWalk can render it as a permission card.
A CodeWalk-shipped extension (`pi -e ./codewalk-bridge.ts`) could also register an `ask_user` tool (questions),
a todo tool + `setWidget`, and custom slash commands. [V mechanism; specific extension = U, to be built]

### 3.5 Security / permissions model [V] (docs/security.md, root README)

"Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access."
"it does not ask for approval before every tool call." Default tools: `read`, `bash`, `edit`, `write` (+ optional
`grep`, `find`, `ls`, `powershell`, `codemode`, `tool_search`); restrict with `--tools`, `--exclude-tools`, `--no-tools`.
**Project trust** (`--approve`/`--no-approve`, `defaultProjectTrust: "always"|"ask"|"never"`, `~/.pi/agent/trust.json`)
only controls loading of `.pi/*` resources; RPC mode cannot show the trust prompt → pass `--approve`/`--no-approve`.
Isolation recommended via containers / Gondolin micro-VM extension / OpenShell.

### 3.6 Sessions storage

`~/.pi/agent/sessions/` grouped by working directory (override `--session-dir`, `PI_CODING_AGENT_SESSION_DIR`, `sessionDir`).
Append-only JSONL tree of entries with stable ids (`docs/session-format.md`). SDK listing: `SessionManager.list(cwd, sessionDir?)`,
`SessionManager.listAll()`, `SessionManager.findById(cwd,id)`, `SessionManager.open(path)`, `.continueRecent(cwd)`, `.forkFrom(...)`.
CLI: `--continue`, `--resume`, `--session <path|id>`, `--session-id <id>`, `--fork <path|id>`, `--no-session`. [V] docs/sessions.md, docs/cli.md, examples/sdk/11-sessions.ts

## 5. Verdict

**Integrable. Best surface: RPC mode behind a host-side bridge.** Two bridge shapes:

1. **Dumb relay** (smallest): host process spawns `pi --mode rpc --approve -e <codewalk-ext.ts>` per open session and
   relays raw JSONL over an authenticated WebSocket; Flutter speaks Pi RPC directly. Bridge adds: session listing
   (read session dir), file search, process lifecycle, auth/TLS. ~1–2 weeks of bridge work + Dart client.
2. **SDK bridge** (Node/Bun): one process hosts many `AgentSession`s via `createAgentSession` / `AgentSessionRuntime`,
   exposes a CodeWalk-shaped API (could even mimic OpenCode's HTTP+SSE shapes). More work, better multi-session.

Effort: **medium**. Risk: **low–medium** (RPC is documented and typed at 1.0; churn is high but additive; no ACP;
approvals/questions/todos must be supplied by a CodeWalk extension). Do **not** depend on `pi-server`/`pi-protocol`
until they drop the "experimental, no compatibility guarantees" label. If CodeWalk builds a generic ACP client,
`pi-acp` gives a cheaper but lossy path (no permission gating, no fs/terminal delegation).

- **Kimi CLI (Moonshot)** — native ACP `kimi acp` (core 3/3 + session 11/11 incl. `session/list`, `session/fork`, `session/close`), plus its own **Wire mode** `kimi --wire` (JSON-RPC 2.0 over stdio, protocol 1.10, methods `initialize`, `prompt`, `steer`, `replay`…). Binaries linux-aarch64/x86_64. [V] https://www.kimi.com/code/docs/en/kimi-code-cli/reference/kimi-acp.html · https://moonshotai.github.io/kimi-cli/en/customization/wire-mode.html · registry
- **GitHub Copilot CLI** — native ACP `npx @github/copilot@1.0.91 --acp`; separately the official **Copilot SDK** (TS/Python/Go/.NET/Java) speaks Content-Length-framed JSON-RPC to `copilot --headless --stdio` or **TCP** `copilot --headless --port 4321` (loopback by default, `--host` to expose). [V] registry; https://github.com/github/copilot-sdk/blob/main/docs/setup/backend-services.md · https://www.freestyle.sh/docs/guides/run-github-copilot-in-a-sandbox
- **Cursor CLI** — native ACP `cursor-agent acp` (binaries for darwin/linux/windows, x86_64 + aarch64). [V] registry `cursor/agent.json`; https://cursor.com/docs/cli/acp
- **Factory Droid** — ACP via `npx droid@0.231.0 exec --output-format acp-daemon`. [V] registry `factory-droid/agent.json`; https://factory.ai/product/cli
- **Goose (now aaif-goose/goose)** — native ACP `goose acp`; `goosed` exposes an undocumented REST+SSE API (~103 endpoints, default 127.0.0.1:3000); maintainers are moving to `goose serve` = ACP over HTTP/WebSocket (already used by a "Goose Mobile" client). [V] registry; https://github.com/aaif-goose/goose/discussions/7697 · https://github.com/aaif-goose/goose/issues/6642
- **OpenAI Codex** — `codex app-server` JSON-RPC 2.0 (JSONL, `jsonrpc` header omitted) over stdio, plus **experimental** `--listen ws://IP:PORT` / unix socket (`codex --remote ws://…`); ACP through official-org adapter `@agentclientprotocol/codex-acp`. [V] https://learn.chatgpt.com/docs/app-server · registry `codex-acp/agent.json` (see also `plan/codex-src/`)
- **Claude Code** — Agent SDK + `stream-json`; ACP through `@agentclientprotocol/claude-agent-acp`. [V] registry `claude-acp/agent.json` (see also `plan/claude-code-src/`)
- **Amp (Sourcegraph)** — `amp -x --stream-json [--stream-json-input]` (Claude-Code-compatible stream-json; multi-turn via `amp threads continue`); TS SDK wraps it; ACP only via community `amp-acp`. [V] https://ampcode.com/news/streaming-json · registry `amp-acp/agent.json`
- **Mistral Vibe** — ACP via bundled `vibe-acp` binary. [V] registry `mistral-vibe/agent.json`
- **Crush (Charm)** — headless `crush run` only; experimental client-server mode over Unix sockets/named pipes (`CRUSH_CLIENT_SERVER=1`, OpenAPI); **no official ACP** (PR #2450 open; community `crush-acp`). [V] https://github.com/charmbracelet/crush/pull/2450 · https://github.com/charmbracelet/crush/discussions/1766
- **OpenCode** (CodeWalk's current backend) — HTTP+SSE server and also `opencode acp`. [V] registry `opencode/agent.json`
