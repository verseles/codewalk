# V2-060C — integrated workspace flow on a disposable host

> **Scope:** private development validation of the CodeWalk v2 workspace
> against a real OpenCode `2.0.22` server, through the same shared root
> screens as the fake integrated flow. This is not a G1–G5 gate, a public
> beta record, an installed-native acceptance or an MVP acceptance.
> Owner issue: [#409](https://github.com/verseles/codewalk/issues/409)
> (roadmap §11.6 Seq 5.3).

## What was observed

The launcher (`tool/ci/live_smoke_v2_opencode.py --unit V2-060C`) fetched the
official `@opencode/cli-linux-arm64@2.0.22` package, verified its SHA-512
integrity and the pinned SHA-256 digests, and ran it as an **owned
foreground** `opencode serve` on `127.0.0.1` with an ephemeral port, an
isolated `HOME`/`XDG_*` tree, a fresh password and a committed disposable
project. The only provider it could reach was a **loopback stub**
(deterministic tokens, `cost` 0). The run was made from the clean committed
revision named in `provenance.json` (`repoTreeDirty: false`).

The run repeats the eight V2-060B baseline capabilities and then the ten
workspace phases. Every file below except this README and `validate.py` is
**generated by the launcher from the recorded run** (`--fixture-out`);
`validation.json` is derived from it by the validator. A capability without a
`passed` marker of its phase is recorded as `missing`, never as a pass.

| Capability | Result | How it was observed |
|---|---|---|
| Baseline (8) | `passed` | Pairing, send, tool/manual/automatic approval, reconnect, Stop and idle Stop, as in V2-060B |
| Workspace pairing | `passed` | The real pairing screen saved the server; the host catalog reloaded before the profile was selected |
| Workspace | `passed` | The projects sidebar and the empty workspace rendered through the real shell |
| Tab | `passed` | Server-created sessions opened as session tabs; tapping a tab switched the open session |
| Send | `passed` | The real composer sent a prompt in the open tab; the native assistant message reports `cost` 0 |
| Steer | `passed` | A second prompt was sent with the steer delivery while the turn was running |
| Stop | `passed` | The live Stop control ended the running turn and Stop became unavailable |
| Approval | `passed` | A native request created over the wire was answered from its card; the server's pending list emptied and no saved rule was written |
| Form | `passed` | A native form was answered from its card; the server settled it with the chosen answer |
| Model switch | `passed` | The selection control switched the session model; the server's session reports the new model |
| Error | `passed` | A stub `401 invalid_api_key` turn rendered the typed error card with its recovery action, without an exception |

## Zero-spend and isolation evidence

- `egress.json`: the audit sampled the owned server's sockets while the live
  suite ran; no non-loopback peer was observed in any sample, and the run
  fails closed on a violation or when the audit itself cannot run.
- `stub-ledger.json`: every provider request is recorded with its scenario
  marker; the run used 7.
- `cleanup.json`: the owned server exited, the temporary tree was removed,
  the owned process group is empty, every owned port was released, the
  host's own listening ports were preserved and the user's own OpenCode
  service was still running afterwards.

## Limitations

- The disposable server ran on this Linux aarch64 host. No Android device, no
  installed client and no Linux x64, Windows or macOS target was exercised;
  installed-platform evidence belongs to V2-078A (Seq 5.4).
- The provider was a loopback stub with `cost` 0, so this evidence proves the
  **CodeWalk client contract**, not provider behaviour.
- The permission and form answered in the workspace were created over the
  native API so the UI had a real pending request to settle.
- The immutable V2-060B fixture (`../live-smoke-060b`) is unchanged; the
  launcher refuses to write a fixture over another unit's.

## Files

| File | Content |
|---|---|
| `capabilities.json` | The marker phase of every capability, written by the launcher |
| `results.json` | Per-capability result states and the limitations |
| `provenance.json` | Version, artifact digests, revision, topology, cost, wall clock |
| `events.json` | The phase markers of the run and the client exit code |
| `markers.txt` | The same markers, one per line |
| `stub-ledger.json` | Every provider request the stub served |
| `egress.json` | The egress audit result |
| `cleanup.json` | The isolation and cleanup proof |
| `validate.py` | Read-only cross-checks over this directory |
| `SHA256SUMS` | The digests of the generated evidence files |
| `validation.json` | The last validator report (derived; excluded from the digests) |

Reproduce from a clean committed tree with:

```bash
python3 tool/ci/live_smoke_v2_opencode.py run \
  --unit V2-060C \
  --root /tmp/opencode/v2-060c-run \
  --evidence-out /tmp/opencode/v2-060c-evidence \
  --fixture-out test/contract/fixtures/opencode/2.0.22/live-smoke-060c \
  --flutter-test test/v2/sessions/live_flow_smoke_test.dart
python3 test/contract/fixtures/opencode/2.0.22/live-smoke-060c/validate.py
```
